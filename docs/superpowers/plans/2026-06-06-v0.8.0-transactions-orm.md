# v0.8.0 — Transactions ORM (core) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add atomic, all-or-nothing transactions to model CRUD via an `async with SurrealDBConnectionManager.transaction() as tx:` context manager and a `tx=` parameter on `save`/`update`/`merge`/`delete`.

**Architecture:** The official SDK 2.0 is single-connection and exposes no transaction object. We therefore use **statement buffering**: a `Transaction` collects each operation's SurrealQL statement (with namespaced bound variables) instead of executing it immediately. On a clean context-manager exit, the buffer is flushed as **one** `client.query("BEGIN TRANSACTION; …; COMMIT TRANSACTION;", vars)` call — atomic server-side. If the `async with` body raises, the buffer is discarded and **nothing** is sent (rollback is free because no statement ran). Reads inside a transaction are out of scope for v0.8.0 (planned for v0.9.0); calling a read/refresh with `tx=` raises a clear error.

**Tech Stack:** Python 3.11+, `surrealdb[pydantic]>=2.0.0,<3.0.0`, Pydantic v2, pytest + pytest-asyncio, ruff, mypy. Tests run against SurrealDB **v2.6.0 and v3.1.3** (Docker).

---

## Scope

**In scope (v0.8.0):**

- `SurrealDBConnectionManager.transaction()` async context manager.
- `Transaction` object (statement buffer + namespaced variables + single-query flush).
- `tx=` parameter on `BaseSurrealModel.save()`, `.update()`, `.merge()`, `.delete()`.
- Atomicity: commit on success, rollback (no-op) on exception.

**Out of scope (later versions):**

- `objects(tx=)` / QuerySet reads under a transaction, savepoints → **v0.9.0**.
- `refresh(tx=)` and any read inside a transaction → raises `SurrealDbError` in v0.8.0.
- Auto-generated IDs inside a transaction (buffered creates need an explicit id) → documented limitation, revisited in v0.9.0.

## Design decisions (locked)

1. **Buffer, then single batched query.** Guaranteed atomic regardless of whether `BEGIN`
   persists across separate RPC calls (Task 1 confirms the batched semantics empirically).
2. **Deferred execution.** `await user.save(tx=tx)` appends a statement and returns `self`
   immediately; the DB write happens at commit. Inside a transaction, `save` requires an
   explicit record id (auto-id is not buffered in v0.8.0).
3. **Statements mirror the SDK methods:**
   - `save` → `CREATE <thing> CONTENT $v;`
   - `update` → `UPDATE <thing> CONTENT $v;`
   - `merge` → `UPDATE <thing> MERGE $v;`
   - `delete` → `DELETE <thing>;`
4. **Trusted record-id interpolation.** The record-id string comes from the model's own
   `RecordID` (already trusted), interpolated like the existing `relate()` does via
   `_get_thing()`. Only the data payload is bound as a `$variable`.
5. **Signals.** `pre_*`/`post_*`/`around_*` signals still fire for `tx=` operations, at
   **buffer time** (consistent with "the operation was requested"). Documented as such.

### ✅ Probe findings (confirmed against running SurrealDB v3.1.3) — APPLY TO ALL TASKS

1. **A batched `BEGIN … COMMIT` is atomic.** COMMIT persists all; CANCEL discards all; a
   failing statement rolls back the whole batch (`probe:c` was not persisted).
2. **🔴 CRITICAL: `client.query()` does NOT raise on a failed transaction — it returns `None`.**
   The SDK only checks the first statement's result (the `BEGIN`, always OK). A mid-transaction
   failure rolls back server-side but `query()` reports nothing → a silent "success". Therefore
   the commit MUST use **`client.query_raw(...)`** and inspect every statement's `status`.
3. **`query_raw()` response shape** (per-statement list under `result`):
   - OK statement: `{"result": <data>, "status": "OK", ...}`
   - Failed tx (example): the root error has `status: "ERR"` with a real `kind` such as
     `AlreadyExists` and a message like "Database record ... already exists"; other statements
     show `status: "ERR"` with `details.kind == "NotExecuted"` / "aborted due to a prior error".
   - **Detection rule:** any item with `status == "ERR"` ⇒ the transaction failed → raise.
     For the message, prefer the first ERR whose `details.kind != "NotExecuted"` (the root cause).
4. **`DELETE <table>` on a never-created table raises `NotFoundError` on 3.x** (no-op on 2.x).
   Every E2E test's cleanup of `DELETE TxUser;` MUST suppress `NotFoundError` (use the
   `_clear(client)` helper defined in Task 3).

These findings are already incorporated into Tasks 2–3 below.

```python
# src/surreal_orm_lite/transaction.py
"""ORM-level transactions for the official SurrealDB SDK 2.0.

The official SDK is single-connection and exposes no transaction object, so a
``Transaction`` buffers each operation's SurrealQL statement (with namespaced bound
variables) and flushes them as a single ``BEGIN TRANSACTION; …; COMMIT TRANSACTION;``
query. A failing statement rolls back the whole batch (verified empirically on
SurrealDB 2.6.x and 3.1); an exception before flush sends nothing at all.

IMPORTANT: the SDK's ``query()`` returns ``None`` (does NOT raise) when a transaction
fails, so commits must use ``query_raw()`` and inspect every statement's ``status`` via
``raise_for_status()``.
"""

from typing import Any

from .exceptions import SurrealDbError


class Transaction:
    """Buffers SurrealQL statements to be committed atomically as one query."""

    def __init__(self) -> None:
        self.statements: list[str] = []
        self.variables: dict[str, Any] = {}
        self._counter: int = 0

    @property
    def is_empty(self) -> bool:
        return not self.statements

    def add(self, statement: str, variables: dict[str, Any] | None = None) -> None:
        """Append a statement, renaming its ``$vars`` with a per-statement prefix.

        Each variable ``$name`` becomes ``$t<N>_name`` to avoid collisions across
        buffered operations.
        """
        prefix = f"t{self._counter}_"
        renamed = statement
        if variables:
            for name, value in variables.items():
                renamed = renamed.replace(f"${name}", f"${prefix}{name}")
                self.variables[f"{prefix}{name}"] = value
        self.statements.append(renamed)
        self._counter += 1

    def build_query(self) -> str:
        """Return the batched ``BEGIN … COMMIT`` query string."""
        if self.is_empty:
            raise ValueError("Cannot commit an empty transaction.")
        body = "\n".join(self.statements)
        return f"BEGIN TRANSACTION;\n{body}\nCOMMIT TRANSACTION;"

    @staticmethod
    def raise_for_status(raw: Any) -> None:
        """Inspect a ``query_raw()`` response and raise if the transaction failed.

        The SDK's ``query()`` silently returns ``None`` on a failed transaction, so the
        commit path uses ``query_raw()`` (full per-statement response) and calls this.
        Any statement with ``status == "ERR"`` means the transaction rolled back. The
        raised message prefers the root cause (the first ERR whose ``details.kind`` is
        not ``"NotExecuted"``), falling back to the first ERR otherwise.
        """
        statements = raw.get("result", []) if isinstance(raw, dict) else []
        errors = [s for s in statements if isinstance(s, dict) and s.get("status") == "ERR"]
        if not errors:
            return
        root = next(
            (e for e in errors if (e.get("details") or {}).get("kind") != "NotExecuted"),
            errors[0],
        )
        message = root.get("result") or "transaction failed"
        raise SurrealDbError(f"Transaction failed and rolled back: {message}")
```

```python
    @classmethod
    @contextlib.asynccontextmanager
    async def transaction(cls) -> Any:
        """Atomic transaction: buffer operations, flush as one BEGIN…COMMIT query.

        Operations called with ``tx=tx`` are buffered. On a clean exit the buffer is
        flushed as a single batched query (atomic server-side). If the body raises, the
        buffer is discarded and nothing is sent (rollback).

        Example::

            async with SurrealDBConnectionManager.transaction() as tx:
                await user.save(tx=tx)
                await order.save(tx=tx)
        """
        tx = Transaction()
        try:
            yield tx
        except Exception:
            # Nothing was sent to the DB (statements are buffered) → rollback is free.
            raise
        else:
            if not tx.is_empty:
                client = await cls.get_client()
                # Use query_raw, NOT query: query() returns None (does not raise) when a
                # transaction fails, so a rolled-back batch would look successful. query_raw
                # gives per-statement status, which raise_for_status inspects (probe #2/#3).
                raw = await client.query_raw(tx.build_query(), tx.variables)
                tx.raise_for_status(raw)
```

Note: `contextlib.asynccontextmanager` requires `import contextlib`, already present.

## Open risk flagged for the implementer

`merge(self, tx=None, **data)` makes `tx` a reserved keyword for `merge`. A model with a
field literally named `tx` could not be merged by keyword. This is acceptable (no realistic
SurrealDB column is named `tx`), but if it becomes a problem, switch to a sentinel
(`merge(self, *, _tx=None, **data)`) in a patch release.
