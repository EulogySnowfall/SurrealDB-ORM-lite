# v0.9.0 — Transactions ORM (QuerySet & savepoints)

- **Date** : 2026-06-06
- **Statut** : Approuvé (design)
- **Version cible** : 0.9.0 (depuis 0.8.0)
- **Phase roadmap** : Palier 1, Phase A — Write-path & atomicité
- **Contrainte structurante** : réalisable avec le SDK officiel
  `surrealdb[pydantic]>=2.0.0,<3.0.0`, **sans SDK custom**.

## Objectif

Étendre les transactions du v0.8.0 (CRUD modèle) au **QuerySet** et aux **opérations
bulk**, et permettre les **lectures dans une transaction**. La référence d'API est le
full ORM [`SurrealDB-ORM`](https://github.com/EulogySnowfall/SurrealDB-ORM), porté sur le
**SDK officiel**.

```python
async with SurrealDBConnectionManager.transaction() as tx:
    users = await User.objects(tx=tx).filter(status="active").exec()
    await User.objects(tx=tx).filter(role="guest").bulk_update(role="member")
```

## Décisions de cadrage (validées avec l'utilisateur)

1. **Modèle d'exécution** : transaction **WebSocket interactive** (BEGIN à l'entrée,
   opérations exécutées immédiatement, COMMIT/CANCEL à la sortie) plutôt que le buffering
   pur du v0.8.0. C'est la seule façon de faire fonctionner les **lectures dans une
   transaction** (l'exemple ci-dessus), car le buffering n'exécute rien avant le commit.
2. **Connexion** : la transaction interactive ouvre une **connexion dédiée** (depuis les
   paramètres stockés : url/user/pass/ns/db), fait BEGIN/ops/COMMIT/CANCEL dessus, puis la
   ferme. La connexion singleton partagée n'est jamais touchée → les opérations concurrentes
   hors-transaction restent sûres, isolation réelle. Ce n'est **pas** un pool (une connexion
   courte et scopée).
3. **Portée hybride HTTP + WS** : on **conserve** le modèle buffering du v0.8.0 comme
   stratégie **HTTP**, et on **ajoute** la stratégie **WS interactive**. La transaction
   choisit selon le schéma de l'URL configurée. C'est exactement ce que fait le full ORM
   (`HTTPTransaction` + `WebSocketTransaction`) → aucune divergence ajoutée entre les deux
   libs ; elles ne diffèrent plus que par le SDK. Aucune régression vs v0.8.0.
4. **Savepoints** : SurrealDB ne supporte pas les savepoints / transactions imbriquées
   (BEGIN/COMMIT/CANCEL à plat uniquement). Ils sont **documentés comme non disponibles**,
   pas simulés (YAGNI).
5. **Lectures dans une transaction HTTP** : impossibles physiquement (HTTP sans état) →
   lèvent une **erreur explicite** plutôt que de renvoyer du vide silencieux (le full ORM
   renvoie du vide, jugé trompeur).

## Différence documentée vs full ORM

Avec l'hybride, **il n'y a aucune divergence de sémantique de transaction** entre lite et
full : les deux supportent buffering HTTP + interactif WS, mêmes capacités. La seule
différence reste le SDK (officiel vs custom). À mentionner dans la doc comparative.

## Pré-requis de validation (spike — à faire en TOUT PREMIER)

> Tout le design WS repose sur une hypothèse : **le SDK officiel maintient l'état de
> transaction entre des appels `query()` successifs sur une même connexion WS**.

- **Confiance** : élevée. Le `WebSocketTransaction` du full ORM le fait (BEGIN, puis ops,
  puis COMMIT sur la même connexion) ; c'est le modèle de session WS documenté de SurrealDB ;
  le SDK officiel est un client mince sur le même protocole RPC.
- **Action** : un test E2E minimal (BEGIN ; CREATE ; SELECT voit le CREATE ; CANCEL ; le
  record a disparu) **avant** de construire le reste. Si l'hypothèse est fausse, on se
  rabat sur buffering pur (WS aussi) + lectures non supportées, et on rouvre le design.

## Architecture

Structure à deux stratégies, dispatchée par `connection_manager.transaction()` selon le
schéma de l'URL configurée. On s'inspire du full ORM tout en restant « lite » (SDK officiel,
`query()` / `query_raw()`).

```text
Transaction (base abstraite)
├── état post-commit (enqueue_post_commit / fire_post_commit)   [conservé du v0.8.0]
├── raise_for_status (statique)                                  [conservé du v0.8.0]
├── interface commune utilisée par les call sites :
│     add(sql, vars) -> list | None      # opération d'écriture
│     run_read(sql, vars) -> list        # opération de lecture
│     is_interactive: bool
│     begin() / commit() / cancel()
│
├── BufferedTransaction      (HTTP)  — logique buffering du v0.8.0
└── InteractiveTransaction   (WS)    — connexion dédiée + BEGIN/ops/COMMIT/CANCEL
```

- `Transaction` reste **exporté** (type de base ; `tx: Transaction` reste valide pour les
  annotations et `isinstance`). Les deux sous-classes concrètes sont des détails internes
  (exportées aussi si utile aux tests).

### Interface commune (contrat pour les call sites)

| Méthode | `BufferedTransaction` (HTTP) | `InteractiveTransaction` (WS) |
| --- | --- | --- |
| `add(sql, vars)` | met en file, renvoie `None` | exécute sur la connexion tx, renvoie les lignes |
| `run_read(sql, vars)` | **lève** `SurrealDbError` (« lecture en tx → WS requis ») | exécute sur la connexion tx, renvoie les lignes |
| `is_interactive` | `False` | `True` |
| `begin()` | marque actif (aucun appel serveur) | ouvre la connexion dédiée + `BEGIN TRANSACTION;` |
| `commit()` | flush `BEGIN…COMMIT` via `query_raw` sur le client **partagé** + `raise_for_status` | `COMMIT TRANSACTION;` (inspecté) puis ferme la connexion |
| `cancel()` | jette la file (aucun appel serveur) | `CANCEL TRANSACTION;` best-effort puis ferme la connexion |

### `BufferedTransaction` (HTTP) — = v0.8.0

Reprend tel quel la logique actuelle de `Transaction` v0.8.0 : `add()` renomme les variables
par préfixe et met en file ; `build_query()` produit `BEGIN TRANSACTION;\n…\nCOMMIT
TRANSACTION;` ; le commit envoie ça via `query_raw()` (sur la connexion partagée) puis
`raise_for_status()`. `run_read()` lève. Comportement v0.8.0 **inchangé** (auto-id en tx
interdit, `refresh(tx=)` interdit).

### `InteractiveTransaction` (WS) — nouveau

- `begin()` : ouvre une `AsyncSurreal` dédiée via `connection_manager._open_client()`
  (connect + signin + use ns/db), puis `query_raw("BEGIN TRANSACTION;")`.
- `add()` / `run_read()` : `query_raw(sql, vars)` sur la connexion tx → `raise_for_status()`
  (un statement en échec « empoisonne » la tx ; on lève immédiatement, l'exception du corps
  déclenche `cancel()`), puis renvoie les lignes dé-enveloppées.
- `commit()` : `query_raw("COMMIT TRANSACTION;")` inspecté ; `finally` ferme la connexion.
- `cancel()` : `query("CANCEL TRANSACTION;")` best-effort ; `finally` ferme la connexion.

### `connection_manager.py`

- Refactor : extraire **`_open_client()`** (créer + connect-si-WS + signin + use une nouvelle
  `AsyncSurreal`, **sans** la mettre en cache). `get_client()` l'utilise pour le singleton ;
  la tx l'utilise pour la connexion dédiée. DRY.
- `transaction()` :
  1. inspecte l'URL configurée → `InteractiveTransaction` si `ws://`/`wss://`, sinon
     `BufferedTransaction`.
  2. `await tx.begin()` (passe les params nécessaires / `_open_client`).
  3. `yield tx`.
  4. sur exception → `await tx.cancel()` ; re-raise.
  5. sinon → `await tx.commit()` puis `await tx.fire_post_commit()`.
  6. `finally` : garantir la fermeture de la connexion dédiée (interactive).
- Sémantique d'exception du v0.8.0 conservée (rollback = `SurrealDbError` ; échec d'un
  handler post-commit ≠ rollback).

### `model_base.py`

- `objects(tx: Transaction | None = None)` : transmet `tx` au `QuerySet`.
- Branches `tx=` de `save/update/merge/delete` : construisent leur SurrealQL (déjà le cas en
  v0.8.0) et appellent **`tx.add(...)`**. En interactif, `add()` exécute immédiatement ; en
  buffering, met en file. Les signaux gardent la **sémantique v0.8.0** : `pre_*` immédiats,
  `around_*` **non émis** en tx, `post_*` **différés** via `enqueue_post_commit`.
- **Renforcements quand `tx.is_interactive`** (sinon comportement v0.8.0) :
  - `save(tx=)` : supporte l'**auto-id** (le `CREATE table CONTENT $data` renvoie le record,
    dont on récupère l'id) ; sur buffering, conserve l'erreur « explicit id required ».
  - `merge(tx=)` : fait un **vrai `refresh()`** via `run_read()` (au lieu d'appliquer les
    champs à la main) ; sur buffering, conserve l'application manuelle v0.8.0.
  - `refresh(tx=)` : **fonctionne** via `run_read()` ; sur buffering, conserve l'erreur
    v0.8.0 (« reads … not supported »), reformulée pour mentionner « connexion WS requise ».

### `query_set.py`

- `QuerySet` stocke `self._tx` (passé par `objects(tx=)` ; helper interne `_with_tx`).
- **Lectures** (`exec`/`first`/`get`/`all`/`count`/`exists`/`sum`/`avg`/`min`/`max`) : passent
  par `_execute_query()`, qui route vers `tx.run_read(sql, vars)` quand `_tx` est défini.
  - `get(id)` et `all()` (qui utilisent `client.select()` hors tx) construisent leur SurrealQL
    (`SELECT * FROM $rid` / `SELECT * FROM table`) et passent par `run_read()` sous tx. La
    gestion `NotFoundError` (table jamais créée → vide) est conservée.
- **Écritures bulk** (`bulk_update`/`bulk_delete`) : passent déjà par `_execute_query()` →
  routées via `tx.add()` sous tx. `bulk_create` sous tx : interactif → `insert` sur la
  connexion tx ; buffering → met en file un statement d'insertion.

## Savepoints (non disponibles)

SurrealDB n'expose pas SAVEPOINT ([Transactions | SurrealQL](https://surrealdb.com/docs/surrealql/transactions)).
Décision :

- Aucune API de savepoint trompeuse.
- Documenter dans le docstring de `transaction()` et dans la ROADMAP que les savepoints /
  transactions imbriquées ne sont pas supportés par SurrealDB.
- Des appels `transaction()` imbriqués ouvrent des **transactions indépendantes** (connexions
  distinctes) — documenté comme tel ; ce ne sont **pas** des savepoints.

## Matrice de capacités (à documenter)

| Opération sous `tx=` | WS (interactif) | HTTP (buffering) |
| --- | --- | --- |
| `save` / `update` / `merge` / `delete` | ✓ immédiat, voit ses writes | ✓ bufferisé, atomique au commit |
| `bulk_update` / `bulk_delete` / `bulk_create` | ✓ | ✓ bufferisé, atomique au commit |
| `exec` / `first` / `get` / `all` / `count` / agrégations | ✓ voit les writes non-committés | ✗ lève « lecture en tx → WS requis » |
| `refresh(tx=)`, auto-id en `save(tx=)` | ✓ | ✗ (comportement v0.8.0 conservé) |
| savepoints / transactions imbriquées | non supporté (SurrealDB) | non supporté (SurrealDB) |

## Critères d'acceptation

1. **Spike** WS interactive validé en E2E (BEGIN → write → read voit le write → CANCEL →
   write disparu).
2. `objects(tx=).filter().exec()` retourne des lignes dans une tx WS ; une lecture voit les
   écritures non-committées de la même tx.
3. `bulk_update` / `bulk_delete` sous tx (WS **et** HTTP) ; rollback sur exception →
   données inchangées ; atomicité d'un mélange read + write (WS).
4. Connexion dédiée : la connexion partagée reste utilisable pendant et après une tx WS.
5. Renforcements WS : auto-id en `save(tx=)`, `refresh(tx=)`.
6. HTTP : transactions d'écriture (CRUD + bulk) fonctionnent comme en v0.8.0 ; les lectures
   en tx lèvent une erreur claire.
7. Savepoints documentés comme non disponibles.
8. Garanties transverses : E2E vert sur **2.6.x ET 3.1**, couverture ≥ 70 %, `ruff` +
   `ruff format` + `mypy` verts.

## Compatibilité ascendante

- ✅ **Préservé** : `transaction()`, `tx=` sur `save`/`update`/`merge`/`delete`, et **tout le
  comportement HTTP du v0.8.0** (buffering).
- ⚠️ **Changements de comportement (uniquement sur connexion WS)** :
  - `save(tx=)` accepte l'auto-id (ne lève plus « explicit id required » en WS).
  - `refresh(tx=)` fonctionne en WS (ne lève plus).
  - `merge(tx=)` fait un vrai refresh en WS.
- 🔧 **Tests v0.8.0 à réécrire** : les tests unitaires ciblant `Transaction.add` /
  `build_query` visent désormais `BufferedTransaction` ; `raise_for_status` conservé.
  `test_save_in_tx_without_id_raises` et `test_refresh_with_tx_raises` deviennent
  **conditionnels au transport** (toujours vrais en HTTP, inversés en WS).
