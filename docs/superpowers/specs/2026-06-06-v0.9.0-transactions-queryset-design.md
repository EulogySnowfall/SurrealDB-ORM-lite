# v0.9.0 — Transactions ORM (QuerySet & savepoints)

- **Date** : 2026-06-06
- **Statut** : Approuvé (design) — **révisé post-spike** (cf. § Validation empirique)
- **Version cible** : 0.9.0 (depuis 0.8.0)
- **Phase roadmap** : Palier 1, Phase A — Write-path & atomicité
- **Contrainte structurante** : réalisable avec le SDK officiel
  `surrealdb[pydantic]>=2.0.0,<3.0.0` (installé : **2.0.0**), **sans SDK custom**.

## Objectif

Étendre les transactions du v0.8.0 (CRUD modèle) au **QuerySet** et aux **opérations
bulk**, et permettre les **lectures dans une transaction** là où le serveur le permet. La
référence d'API est le full ORM [`SurrealDB-ORM`](https://github.com/EulogySnowfall/SurrealDB-ORM),
porté sur le **SDK officiel**.

```python
async with SurrealDBConnectionManager.transaction() as tx:
    users = await User.objects(tx=tx).filter(status="active").exec()   # 3.x (WS) : voit les writes en cours
    await User.objects(tx=tx).filter(role="guest").bulk_update(role="member")
```

## Validation empirique (spike — réalisé le 2026-06-06)

Le SDK officiel **2.0.0 expose une API de transaction native** (vérifiée dans
`surrealdb/connections/async_ws.py`) :

- `txn_id = await client.begin()` → UUID de transaction
- `await client.commit(txn_id)` / `await client.cancel(txn_id)`
- `txn_id=` accepté par `query`, `query_raw` et les méthodes CRUD (`create`, `update`,
  `merge`, `delete`, `select`, `insert`, `upsert`…)

**Résultats du spike (testé sur les deux serveurs)** :

| Serveur          | `client.begin()`                  | Lecture dans la tx | Isolation (lecture hors tx) | commit/cancel |
| ---------------- | --------------------------------- | ------------------ | --------------------------- | ------------- |
| **3.1.3** (WS)   | ✓ renvoie un UUID                 | voit les writes ✓  | ne voit pas les writes ✓    | ✓             |
| **2.6.5** (WS)   | ✗ `NotFoundError: Method not found` | —                  | —                           | —             |

**Conclusions structurantes** :

1. L'interactif passe par l'**API native** (`begin()` + `txn_id=`), **pas** par
   `query("BEGIN TRANSACTION")` (qui échoue : le serveur ne garde pas l'état de tx entre
   appels RPC). Le spike initial avait échoué pour cette raison.
2. Le `txn_id` **isole nativement** sur la **connexion partagée** : une lecture sans
   `txn_id` ne voit pas les écritures de la tx. → **pas de connexion dédiée nécessaire**.
3. L'API de transaction native est **SurrealDB 3.x uniquement** (absente en 2.6.x). En
   2.6.x (et en HTTP, et embedded), on se rabat sur le **buffering** (un seul
   `BEGIN … COMMIT` envoyé via `query_raw`), qui fonctionne déjà (modèle v0.8.0).

## Décisions de cadrage (validées avec l'utilisateur)

1. **Modèle d'exécution** : transaction **interactive via l'API native du SDK**
   (`begin()`/`commit(txn_id)`/`cancel(txn_id)` + `txn_id=` sur les opérations) quand le
   serveur le supporte ; sinon **buffering** (v0.8.0). Seul l'interactif permet les
   **lectures dans une transaction**.
2. **Connexion** : **connexion singleton partagée + `txn_id`** (l'isolation est native,
   prouvée par le spike). **Pas** de connexion dédiée (décision révisée : devenue inutile).
3. **Portée hybride, basée sur la capacité serveur** (et non plus seulement le schéma
   d'URL) :
   - **WS + SurrealDB 3.x** → interactif natif (lectures dans la tx OK).
   - **WS + SurrealDB 2.6.x**, ou **HTTP**, ou embedded → buffering (écritures bufferisées,
     atomiques au commit ; lectures dans la tx non disponibles).
   La détection se fait par **probe** : `transaction()` tente `client.begin()` sur une
   connexion WS ; un `NotFoundError` (méthode absente, cas 2.6.x) bascule en buffering.
4. **Savepoints** : SurrealDB ne supporte pas les savepoints / transactions imbriquées.
   **Documentés comme non disponibles**, pas simulés (YAGNI).
5. **Lectures dans une transaction non-interactive** (2.6.x / HTTP) : impossibles → lèvent
   une **erreur explicite** plutôt que de renvoyer du vide silencieux.

## Différence vs full ORM & promesse « lite »

- Le full ORM (SDK custom) implémente l'interactif à sa façon ; lite utilise l'**API
  native du SDK officiel**. Sémantiquement équivalent côté utilisateur (mêmes capacités
  d'écriture transactionnelle ; lectures-en-tx selon le serveur).
- **Promesse lite (2.6.x + 3.1) préservée** : les transactions d'écriture (CRUD + bulk)
  marchent sur **les deux** ; les **lectures dans une transaction** sont un **bonus 3.x**.
  À documenter clairement (matrice ci-dessous).

## Architecture

Deux stratégies derrière une interface commune ; `connection_manager.transaction()` choisit
selon la capacité serveur (probe `begin()`).

```text
Transaction (base abstraite)
├── machinerie post-commit (enqueue_post_commit / fire_post_commit)   [conservé du v0.8.0]
├── raise_for_status (statique)                                        [conservé du v0.8.0]
├── interface commune utilisée par les call sites :
│     add(sql, vars) -> list | None      # écriture
│     run_read(sql, vars) -> list        # lecture
│     is_interactive: bool
│     commit() / cancel()
│
├── BufferedTransaction(client)            — buffering (v0.8.0), HTTP & WS-2.6.x
└── InteractiveTransaction(client, txn_id) — API native du SDK (3.x), connexion partagée
```

- `Transaction` reste **exporté** (type de base). Les deux sous-classes sont des détails
  internes (exportées aussi pour les tests).
- **`begin` n'est pas dans l'interface** : le probe/begin est géré par
  `connection_manager.transaction()` (il a besoin du résultat de `begin()` pour choisir la
  stratégie et obtenir le `txn_id`).

### Interface commune (contrat pour les call sites)

| Méthode | `BufferedTransaction` (HTTP / WS-2.6.x) | `InteractiveTransaction` (WS 3.x) |
| --- | --- | --- |
| `add(sql, vars)` | met en file, renvoie `None` | `query_raw(sql, vars, txn_id=…)` + `raise_for_status`, renvoie les lignes |
| `run_read(sql, vars)` | **lève** `SurrealDbError` (« lecture en tx → WS + 3.x requis ») | `query(sql, vars, txn_id=…)`, renvoie les lignes |
| `is_interactive` | `False` | `True` |
| `commit()` | flush `BEGIN…COMMIT` via `query_raw` sur le client partagé + `raise_for_status` | `client.commit(txn_id)` |
| `cancel()` | jette la file (aucun appel serveur) | `client.cancel(txn_id)` best-effort |

### `BufferedTransaction` (HTTP / WS-2.6.x) — = v0.8.0

Reprend la logique v0.8.0 : `add()` renomme les variables par préfixe et met en file ;
`build_query()` produit `BEGIN TRANSACTION;\n…\nCOMMIT TRANSACTION;` ; `commit()` envoie ça
via `query_raw()` (sur le client partagé) + `raise_for_status()`. `run_read()` lève.
Comportement v0.8.0 inchangé (auto-id en tx interdit, `refresh(tx=)` interdit).

### `InteractiveTransaction` (WS 3.x) — nouveau

- Construit avec `(client, txn_id)` (le `txn_id` vient de `client.begin()`, fait par le
  manager).
- `add(sql, vars)` : `raw = await client.query_raw(sql, vars, txn_id=txn_id)` →
  `raise_for_status(raw)` → renvoie `raw["result"][-1]["result"]`.
- `run_read(sql, vars)` : `return await client.query(sql, vars, txn_id=txn_id)`.
- `commit()` : `await client.commit(txn_id)`.
- `cancel()` : `await client.cancel(txn_id)` (best-effort, suppress).

### `connection_manager.py`

- `transaction()` (recâblé) :
  1. `client = await get_client()`.
  2. Si l'URL est `ws://`/`wss://` : tenter `txn_id = await client.begin()`.
     - succès → `InteractiveTransaction(client, txn_id)`.
     - `NotFoundError` (2.6.x) → `BufferedTransaction(client)`.
  3. Sinon (HTTP) → `BufferedTransaction(client)`.
  4. `yield tx` ; sur exception → `await tx.cancel()` + re-raise ; sinon →
     `await tx.commit()` + `await tx.fire_post_commit()`.
- Sémantique d'exception du v0.8.0 conservée (rollback = `SurrealDbError` ; échec d'un
  handler post-commit ≠ rollback).
- **Pas** d'extraction de `_open_client` ni de connexion dédiée (abandonnés).

### `model_base.py`

- `objects(tx: Transaction | None = None)` : transmet `tx` au `QuerySet`.
- Branches `tx=` de `save/update/merge/delete` : construisent leur SurrealQL et appellent
  **`await tx.add(...)`**. Signaux : sémantique v0.8.0 — `pre_*` immédiats, `around_*` non
  émis en tx, `post_*` différés via `enqueue_post_commit`.
- **Renforcements quand `tx.is_interactive`** (sinon comportement v0.8.0) :
  - `save(tx=)` : auto-id (le `CREATE` renvoie le record) ; buffering → erreur « explicit id ».
  - `merge(tx=)` : vrai `refresh()` via `run_read()` ; buffering → application manuelle v0.8.0.
  - `refresh(tx=)` : fonctionne via `run_read()` ; buffering → erreur (read non supporté).

### `query_set.py`

- `QuerySet` stocke `self._tx` (via `objects(tx=)`).
- **Lectures** (`exec`/`first`/`get`/`all`/`count`/`exists`/agrégations) → `_execute_query()`
  route vers `tx.run_read(...)` quand `_tx` est défini (NotFoundError → vide).
- **Écritures bulk** (`bulk_update`/`bulk_delete`/`bulk_create`) → `tx.add(...)` quand `_tx`
  est défini.

## Savepoints (non disponibles)

SurrealDB n'expose pas SAVEPOINT ([Transactions | SurrealQL](https://surrealdb.com/docs/surrealql/transactions)).
Pas d'API trompeuse ; documenté dans le docstring de `transaction()` et la ROADMAP. Des
`transaction()` imbriqués → transactions indépendantes (pas des savepoints).

## Matrice de capacités (à documenter)

| Opération sous `tx=` | WS + SurrealDB 3.x (interactif natif) | WS 2.6.x / HTTP (buffering) |
| --- | --- | --- |
| `save` / `update` / `merge` / `delete` | ✓ immédiat, isolé, voit ses writes | ✓ bufferisé, atomique au commit |
| `bulk_update` / `bulk_delete` / `bulk_create` | ✓ | ✓ bufferisé, atomique au commit |
| `exec` / `first` / `get` / `all` / `count` / agrégations | ✓ voit les writes non-committés | ✗ lève « lecture en tx → WS + 3.x requis » |
| `refresh(tx=)`, auto-id en `save(tx=)` | ✓ | ✗ (comportement v0.8.0 conservé) |
| savepoints / transactions imbriquées | non supporté (SurrealDB) | non supporté (SurrealDB) |

## Critères d'acceptation

1. Spike native validé (déjà fait) : `begin()`+`txn_id` → lecture voit ses writes, isolation,
   commit/cancel, sur 3.1 ; `NotFoundError` sur 2.6.x.
2. `objects(tx=).filter().exec()` retourne des lignes dans une tx **3.x** ; une lecture voit
   les écritures non-committées de la même tx.
3. `bulk_update` / `bulk_delete` sous tx (3.x **et** 2.6.x/HTTP) ; rollback sur exception →
   données inchangées ; atomicité d'un mélange read + write (3.x).
4. `2.6.x`/HTTP : transactions d'écriture (CRUD + bulk) OK ; lectures en tx lèvent une erreur
   claire.
5. Renforcements 3.x : auto-id en `save(tx=)`, `refresh(tx=)`.
6. Savepoints documentés non disponibles.
7. Garanties transverses : E2E vert sur **2.6.5 ET 3.1.3**, couverture ≥ 70 %, `ruff` +
   `ruff format` + `mypy` verts.

## Compatibilité ascendante

- ✅ **Préservé** : `transaction()`, `tx=` sur `save`/`update`/`merge`/`delete`, et tout le
  comportement buffering du v0.8.0 (désormais sur HTTP **et** WS-2.6.x).
- ⚠️ **Changements (uniquement sur WS + 3.x)** : `save(tx=)` accepte l'auto-id ;
  `refresh(tx=)` fonctionne ; `merge(tx=)` fait un vrai refresh.
- 🔧 **Tests v0.8.0 à réécrire** : unitaires `add`/`build_query` → `BufferedTransaction` ;
  `raise_for_status` conservé. `test_save_in_tx_without_id_raises` /
  `test_refresh_with_tx_raises` deviennent **conditionnels à la capacité serveur** (vrais en
  buffering ; inversés en interactif 3.x).
