# v0.10.0 — `upsert()` + `update_or_create()` / `get_or_create()`

- **Date** : 2026-06-07
- **Statut** : Approuvé (design) — validé par spike (cf. § Validation empirique)
- **Version cible** : 0.10.0 (depuis 0.9.0)
- **Phase roadmap** : Palier 1, Phase A — Write-path & atomicité
- **Contrainte structurante** : réalisable avec le SDK officiel
  `surrealdb[pydantic]>=2.0.0,<3.0.0` (installé : **2.0.0**), **sans SDK custom**.

## Objectif

Offrir une insertion-ou-mise-à-jour **idempotente**, à deux niveaux :

1. **`model.upsert()`** — insère le record s'il est absent, le remplace sinon, à partir
   d'un **id explicite** (primitive SDK native `upsert()`).
2. **`QuerySet.update_or_create()` / `QuerySet.get_or_create()`** — variantes
   « basées sur des critères » à la Django : on cherche un record qui matche les
   critères, on le crée ou on le met à jour, et on renvoie `(instance, created)`.

```python
# 1) upsert par id (remplace tout le record)
user = User(id="alice", name="Alice", status="active")
await user.upsert()                       # CREATE si absent, REPLACE sinon

# 2) update_or_create / get_or_create par critères
user, created = await User.objects().update_or_create(
    email="alice@example.com",            # critères de recherche
    defaults={"name": "Alice", "status": "active"},
)
user, created = await User.objects().get_or_create(
    email="bob@example.com",
    defaults={"name": "Bob"},
)
```

La référence d'API est le full ORM
[`SurrealDB-ORM`](https://github.com/EulogySnowfall/SurrealDB-ORM) (qui utilise `upsert()`
en interne dans `save()`), porté sur le **SDK officiel** et étendu avec les surfaces
publiques `upsert()` / `update_or_create()` / `get_or_create()`.

## Validation empirique (spike — réalisé le 2026-06-07)

Spike exécuté sur **3.1.3 (8001)** ET **2.6.5 (8002)** ; **comportement identique sur les
deux lignes** :

| Vérification | 3.1.3 | 2.6.5 |
| --- | --- | --- |
| `client.upsert(rid, data)` crée le record absent | ✓ | ✓ |
| `client.upsert(rid, data)` re-appelé → **REPLACE** total (les champs absents disparaissent) | ✓ | ✓ |
| `UPSERT t CONTENT $d WHERE c RETURN BEFORE` → `[None]` en création, `[{...}]` en update | ✓ | ✓ |
| `UPSERT … WHERE` quand **2 rows** matchent → met à jour **les 2** (pas d'erreur) | ✓ | ✓ |

**Conclusions structurantes** :

1. La primitive native `upsert()` est une **CONTENT (REPLACE total)**, pas un merge —
   conforme à la sémantique SurrealQL `UPSERT … CONTENT`. Disponible sur **les deux** lignes.
2. `UPSERT … WHERE` brut **n'enforce pas** l'unicité du match : il met à jour **tous** les
   records qui matchent, silencieusement. Or la roadmap exige « lève une erreur explicite si
   plusieurs records matchent ». ⇒ on **n'utilise pas** `UPSERT … WHERE` brut pour
   `update_or_create` ; on fait un **SELECT-guard + écriture ciblée par id** (cf. Architecture).
3. Aucune primitive 3.x-only n'est requise. La feature est **identique 2.6.x ↔ 3.x**.

## Décisions de cadrage

1. **`model.upsert()` exige un id explicite.** Un upsert sans id n'a rien à matcher
   (auto-id ⇒ toujours une création) ; on lève `SurrealDbError` pour éviter une surprise
   silencieuse. (Les créations auto-id passent par `save()`.)
2. **`upsert()` est un REPLACE total** (sémantique native du SDK), documenté comme tel :
   tout champ omis du modèle disparaît. Pour une mise à jour partielle, `merge()` reste la
   bonne méthode.
3. **`update_or_create` / `get_or_create` n'utilisent PAS `UPSERT … WHERE`** (cf. spike) :
   - SELECT des records qui matchent les critères ;
   - **0 match** → CREATE (critères + defaults), `created=True` ;
   - **1 match** → pour `update_or_create` : UPDATE ciblé par id (critères + defaults),
     `created=False` ; pour `get_or_create` : renvoyé tel quel, `created=False` ;
   - **>1 match** → `SurrealDbError` explicite (« multiple records match »).
4. **Sémantique des `defaults`** (alignée Django) : `defaults` est un dict de valeurs.
   - `update_or_create` : écrit `criteria ∪ defaults` à la création **et** à la mise à jour.
   - `get_or_create` : `criteria ∪ defaults` **uniquement à la création** ; sur match
     existant, aucune écriture.
5. **Critères = égalité simple** (`field=value`), pas de lookups `__gt` etc. (YAGNI : Django
   accepte les lookups mais `defaults` ne s'y applique qu'à la création ; on garde le scope
   minimal de la roadmap : recherche par égalité).
6. **Pas de dépendance à une transaction interactive.** Le SELECT-guard + écriture ciblée
   marche en client simple sur **les deux** lignes (le SELECT et le write par id sont deux
   appels). La petite fenêtre TOCTOU est documentée (identique au fallback non-atomique de
   Django) ; aucune primitive 2.6.x ne la ferme.
7. **`tx=` sur `model.upsert()`** : bufferise `UPSERT {id} CONTENT $data;` via `tx.add(...)`,
   cohérent avec `save/update/merge/delete(tx=)`. (Les `update_or_create`/`get_or_create`
   composites ne prennent **pas** `tx=` dans ce jalon — YAGNI, hors scope roadmap.)

## API publique

### `BaseSurrealModel.upsert(tx: Transaction | None = None) -> Self`

- Exige `self._record_id()` non `None` → sinon `SurrealDbError`.
- Sans `tx` : `await client.upsert(record_id, data)` (data = `model_dump(exclude={"id"})`),
  puis applique le record retourné à `self`. Renvoie `self`.
- Avec `tx` : `await tx.add(f"UPSERT {record_id} CONTENT $data;", {"data": data})` ; en
  interactif, applique le row retourné à `self` ; renvoie `self`.
- **Signaux** : même schéma que `save()` (`pre_save`/`around_save`/`post_save`, `created`
  best-effort = `True`), avec la même gestion `tx` (around non émis en tx, post différé).
  Justification : un upsert est sémantiquement un « save » (create-or-replace).

### `QuerySet.update_or_create(defaults: dict | None = None, **criteria) -> tuple[model, bool]`

- `criteria` non vide requis → sinon `SurrealDbError` (un upsert sans critère est ambigu).
- SELECT `* FROM {table} WHERE <criteria>` (paramétré, anti-injection via le builder existant).
- 0 → CREATE `criteria ∪ defaults` ; 1 → UPDATE par id avec `criteria ∪ defaults` ;
  >1 → `SurrealDbError`.
- Renvoie `(instance, created)`.

### `QuerySet.get_or_create(defaults: dict | None = None, **criteria) -> tuple[model, bool]`

- Même lookup. 0 → CREATE `criteria ∪ defaults`, `created=True` ; 1 → renvoyé tel quel,
  `created=False` ; >1 → `SurrealDbError`.

## Architecture

### `model_base.py`

- `_do_upsert(tx) -> tuple[Self, bool]` : logique pure (REPLACE natif / buffered), miroir de
  `_do_save`.
- `upsert(tx=None) -> Self` : wrapper signaux, miroir de `save()`.

### `query_set.py`

- Helper privé `_lookup_for_criteria(criteria) -> list[model]` : compile un `SELECT` paramétré
  via le builder de filtres existant (`build_filter_condition`) et exécute (réutilise
  `_execute_query`). Garde la cohérence anti-injection.
- `update_or_create(defaults=None, **criteria)` et `get_or_create(defaults=None, **criteria)` :
  orchestrent SELECT-guard → CREATE/UPDATE ciblé, construisent l'instance modèle, renvoient
  `(instance, created)`.
- Les écritures par id passent par le client SDK (`client.create(rid, data)` /
  `client.update(rid, data)`), pas par `query()` brut, pour rester sur les méthodes natives.

### `__init__.py` / `pyproject.toml`

- `version = "0.10.0"`, `__version__ = "0.10.0"`. Aucun **nouveau symbole exporté** : les
  trois méthodes vivent sur des classes déjà exportées (`BaseSurrealModel`, `QuerySet`).

## Critères d'acceptation

1. `model.upsert()` crée un record absent ; un second `upsert()` **remplace** (champ retiré
   disparaît). Sans id → `SurrealDbError`. (E2E sur 3.1 **et** 2.6.x.)
2. `update_or_create()` : `created=True` à la 1re fois, `created=False` ensuite ; pas de
   doublon ; `defaults` appliqués à la création **et** à la mise à jour.
3. `get_or_create()` : `created=True` à la 1re fois, `created=False` ensuite **sans** écraser
   le record existant ; `defaults` appliqués uniquement à la création.
4. `>1 match` → `SurrealDbError` (E2E : on insère 2 records matchant les critères).
5. `update_or_create()`/`get_or_create()` sans critère → `SurrealDbError`.
6. `upsert(tx=)` bufferisé : commit persiste, rollback annule (E2E).
7. Transverses : E2E vert sur **2.6.5 ET 3.1.3**, couverture ≥ 70 %, `ruff` +
   `ruff format` + `mypy` verts.
