# v0.11.0 — `patch()` & atomic field/array operations — Design

- **Date**: 2026-06-07
- **Status**: Approved (design)
- **Target version**: 0.11.0
- **Roadmap**: Tier 1, Phase A — Write-path & atomicity
- **SDK primitive**: native `patch()` (JSON Patch, RFC 6902) + SurrealQL `UPDATE … SET` array/arithmetic functions
- **Constraint**: official SDK only (`surrealdb[pydantic]>=2.0.0,<3.0.0`); all SDK imports via
  `_sdk.py`; anything without a native SDK method goes through `client.query()`.

## Goal

Allow granular, server-side mutations of a record without read-modify-write of the whole
document. Two layers:

1. **`patch()`** — a thin, faithful wrapper over the SDK's native JSON Patch (RFC 6902), on
   the model instance (single record) and on the QuerySet (whole table / filtered set).
2. **Ergonomic atomic helpers** — `atomic_append` / `atomic_set_add` / `atomic_remove` /
   `atomic_increment` — for the common array/counter mutations, each compiled to an atomic
   server-side `UPDATE … SET` so concurrent callers don't clobber each other.

## SDK primitives used

- `client.patch(record, ops)` — native SDK method; runs `UPDATE $record PATCH $data` where
  `data` is a list of JSON Patch operations. Verified present in the pinned SDK with signature
  `patch(record, data, session_id=None, txn_id=None)`. Returns the updated record dict.
- `client.query(sql, vars)` — for the atomic helpers (no native SDK method) and for the
  table-level QuerySet patch. Uses SurrealQL `array::append` / `array::add` /
  `array::complement` and numeric `+=`, and `UPDATE {table} PATCH $ops [WHERE …]`.

## Capability dispatch — 2.6.x vs 3.x

**This feature behaves identically on SurrealDB 2.6.x and 3.x.** That is a deliberate design
choice, not luck. Empirical probing on both server lines (3.1.3 on :8001, 2.6.5 on :8002)
found that the bare array operators **diverge** between versions:

| SurrealQL | 3.1.3 | 2.6.5 | Used by lite? |
| --------- | ----- | ----- | ------------- |
| `arr -= v` | removes **all** occurrences | removes **only the first** | ❌ avoided |
| `arr += v` (array) | appends **with** duplicates | appends **with** duplicates | ❌ avoided (not set-add) |
| `array::append(arr, v)` | append (dups ok) | append (dups ok) | ✅ `atomic_append` |
| `array::add(arr, v)` | set-add (no dup) | set-add (no dup) | ✅ `atomic_set_add` |
| `array::complement(arr, [v])` | removes **all** occurrences | removes **all** occurrences | ✅ `atomic_remove` |
| `num += n` (number) | increments | increments | ✅ `atomic_increment` |
| `UPDATE rid PATCH $ops` (JSON Patch) | works | works | ✅ `patch` |
| `UPDATE table PATCH $ops WHERE …` | works | works | ✅ `QuerySet.patch` |

By picking the version-portable **functions** (`array::append` / `array::add` /
`array::complement`) over the version-dependent **operators** (`-=`, array `+=`), every op in
v0.11.0 produces the same result on both DB lines. (The full ORM's `atomic_set_add` via `+=`
and `atomic_remove` via `-=` are version-buggy by this measure; lite deliberately does not
copy them.) There is therefore **no `pytest.skip` capability gate** in this feature.

The only axis that still varies is the existing transaction model (unchanged from v0.8–v0.9):
buffered on HTTP / 2.6.x, native-interactive on WS + 3.x. `patch()`/atomic ops inherit that
behaviour through `tx=`.

## Public API

### Instance methods (`BaseSurrealModel`)

All require an explicit id (raise `SurrealDbError` otherwise, like `upsert()`), accept
`tx: Transaction | None = None`, and return `Self`. On the non-tx and interactive-tx paths the
server's returned row is applied to `self` (via the existing `_apply_record`); on a **buffered**
tx the result is not yet known, so `self` is left stale (documented — identical caveat to
`merge(tx=)`).

```python
await user.patch([
    {"op": "replace", "path": "/age", "value": 26},
    {"op": "add", "path": "/tags/-", "value": "premium"},
    {"op": "remove", "path": "/settings/notifications"},
])

await post.atomic_append("tags", "python")      # array::append — duplicates allowed
await post.atomic_set_add("editors", "alice")   # array::add     — no duplicate
await post.atomic_remove("tags", "spam")        # array::complement — removes ALL "spam"
await counter.atomic_increment("views")         # += 1 (default)
await counter.atomic_increment("score", 5)      # += 5
```

| Method | Emitted statement (non-tx via `client.patch`/`client.query`) |
| ------ | ------------------------------------------------------------- |
| `patch(operations, tx=None)` | `client.patch(rid, operations)` → `UPDATE rid PATCH $data` |
| `atomic_append(field, value, tx=None)` | `UPDATE rid SET {field} = array::append({field}, $value)` |
| `atomic_set_add(field, value, tx=None)` | `UPDATE rid SET {field} = array::add({field}, $value)` |
| `atomic_remove(field, value, tx=None)` | `UPDATE rid SET {field} = array::complement({field}, [$value])` |
| `atomic_increment(field, amount=1, tx=None)` | `UPDATE rid SET {field} += $amount` |

In a transaction the statement is buffered/executed via `tx.add(sql, vars)` exactly like
`merge(tx=)`. For `patch()` the buffered/interactive SurrealQL is `UPDATE rid PATCH $data`
(equivalent to the native call), so all three paths agree.

### QuerySet method

```python
n = await User.objects().filter(status="trial").patch([
    {"op": "replace", "path": "/plan", "value": "free"},
])                                    # patch all matching rows; returns the count
n = await User.objects().patch([...]) # no filter → whole table
```

`QuerySet.patch(operations) -> int` mirrors `bulk_update`: build the parameterized `WHERE`
from the queryset filters, emit `UPDATE {table} PATCH $_ops{where};`, bind `operations` as
`$_ops`, return the number of affected rows. Participates in `objects(tx=)` like the other
bulk ops.

### Validation (`utils.py`)

- `validate_json_pointer(path: str, context="path") -> None` — RFC 6901: accept the empty
  string (whole document) or a `/`-prefixed string; non-string or other shapes raise
  `ValueError`.
- `validate_patch_operations(operations: Any) -> None` —
  - must be a non-empty `list`; each element a `dict`;
  - `op` present and in `{add, remove, replace, move, copy, test, change}`;
  - `path` present and a valid JSON Pointer;
  - `add` / `replace` / `test` / `change` require a `value` key;
  - `move` / `copy` require a valid JSON Pointer `from` key;
  - clear `ValueError` messages on every failure.
- Atomic-op `field` names are validated with the existing `validate_field_name` (dotted nested
  paths allowed); the value is always passed as a bound `$value`, never interpolated.

JSON Patch `operations` reach the SDK / SurrealQL as **bound data** (`$data` / `$_ops`), not
string-interpolated, so the path/value content is not an injection vector;
`validate_patch_operations` exists for fast, clear errors, not as the security boundary.

## Error handling

- Missing id → `SurrealDbError` ("requires an explicit id"), like `upsert()`.
- Invalid operations / pointer / field → `ValueError` from the validators.
- SDK / server errors propagate as today (structured SDK exceptions; the existing
  `SurrealError` hierarchy via `_sdk.py`).
- Patching a non-existent record: the SDK's `patch()` returns nothing / `None` for a missing
  id (no raise); `self` is left unchanged. Documented; not treated as an error (consistent
  with SurrealDB's UPDATE-of-nothing semantics).

## Deliberate scope decisions

- **No signals.** `patch()` and the atomic helpers do not emit `pre/post/around_update`
  signals. The set of "changed fields" is ambiguous for an arbitrary JSON Patch, and these
  are intentionally low-level atomic primitives; callers who need lifecycle hooks use
  `merge()`/`save()`. Documented in the docstrings and the README.
- **Atomic helpers are instance methods** (per `post.atomic_append(...)`), not classmethods.
- **`atomic_increment` default `amount=1`** for the common counter case.
- No new public exports: every entry point is a method on the already-exported
  `BaseSurrealModel` / `QuerySet`.

## Acceptance criteria

1. `patch()` applies add/replace/remove ops to a single record; the instance reflects the
   result (non-tx). Green on :8001 and :8002.
2. Each atomic helper has the documented effect, including the portability cases:
   `atomic_remove` removes **all** occurrences and `atomic_set_add` adds **no duplicate** on
   **both** DB lines.
3. `atomic_increment` increments by `amount` (default 1), works for negative amounts.
4. `patch()` requires an explicit id (raises otherwise); invalid operations raise `ValueError`.
5. `QuerySet.patch()` patches a filtered set and the whole table; returns the affected count.
6. `patch()`/atomic ops participate in a transaction: buffered tx commits the change and a
   rollback discards it; interactive tx (3.x) applies the returned row to `self`.
7. Quality gates: `ruff format --check`, `ruff check`, `mypy src/` clean; coverage ≥ 70 %.
