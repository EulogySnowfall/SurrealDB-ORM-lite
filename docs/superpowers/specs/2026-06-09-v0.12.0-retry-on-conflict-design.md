# v0.12.0 — `retry_on_conflict` & optimistic concurrency — Design

- **Date**: 2026-06-09
- **Status**: Approved (design)
- **Target version**: 0.12.0
- **Roadmap**: Tier 1, Phase A — Write-path & atomicity
- **SDK primitive**: none new — builds on the existing transactions (v0.8/v0.9) + retry logic
- **Constraint**: official SDK only (`surrealdb[pydantic]>=2.0.0,<3.0.0`); all SDK imports via
  `_sdk.py`; anything without a native SDK method goes through `client.query()`.

## Goal

Make the read-modify-write / optimistic-concurrency pattern usable: when a transaction fails
because a concurrent writer changed a record SurrealDB rolls it back with a **retryable**
conflict. v0.12.0 adds:

1. **`retry_on_conflict(...)`** — an async decorator that re-invokes the wrapped coroutine
   (which opens its own `transaction()`) with exponential backoff + jitter, but **only** when
   the failure is a retryable conflict.
2. **`SurrealDbConflictError`** — one typed exception for "retryable transaction conflict",
   raised consistently on **both** transaction strategies, so users can `except` it and the
   decorator can detect it by type.
3. **`is_conflict_error(exc)`** — the public predicate the decorator uses, exported for callers
   who want to write their own retry loop.

This is the lite re-implementation of the full ORM's `retry_on_conflict` (full ORM:
`surreal_orm/utils.py`), against the official SDK and the existing ORM transaction layer
(the full ORM's `TransactionConflictError` lives in its custom `surreal_sdk`, which is out of
scope for lite — lite defines its own exception).

## SDK primitives used

- **No new SDK method.** Conflicts are produced by the server and surfaced through the existing
  transaction paths:
  - **Interactive (WS + 3.x)**: the conflict is raised by the SDK at `client.commit(txn_id)`
    as `surrealdb.errors.InternalError` (a `ServerError` → `SurrealError`), message
    `"Transaction conflict: Write conflict, retry the transaction. This transaction can be
retried"`.
  - **Buffered (HTTP / 2.6.x WS)**: `query_raw()` returns per-statement `status == "ERR"`; the
    commit statement's message is `"Cannot COMMIT: Transaction conflict: … This transaction can
be retried"` (3.x) or `"…Failed to commit transaction due to a read or write conflict. This
transaction can be retried"` (2.6.5). `Transaction.raise_for_status` turns this into the
    ORM exception.
- `asyncio.sleep` for backoff; `random` for jitter (standard library, SDK-independent).

All four behaviours above were reproduced empirically on :8001 (3.1.3) and :8002 (2.6.5) before
this design (two interleaved transactions forcing a write-write conflict).

## Capability dispatch — 2.6.x vs 3.x

The decorator and the exception behave **the same on both DB lines** — `retry_on_conflict`
catches the same `SurrealDbConflictError` regardless of strategy. What differs is **how often a
conflict happens**, which is a property of the server engine, not the ORM:

| Aspect                 | SurrealDB 2.6.5                                                     | SurrealDB 3.1.3                                                    | Notes                                                                          |
| ---------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| Conflict surfaced as   | `SurrealDbConflictError`                                            | `SurrealDbConflictError`                                           | normalised by the ORM on both                                                  |
| Strategy in play       | buffered (`BEGIN…COMMIT`)                                           | interactive (`txn_id`) on WS                                       | unchanged from v0.9.0                                                          |
| How a conflict appears | per-statement `ERR` in `query_raw` (message carries the cause)      | raised by `client.commit(txn_id)` (interactive) / `ERR` (buffered) | —                                                                              |
| Conflict frequency     | rarer (engine serialises more); reproducible under high concurrency | optimistic MVCC → conflicts are the normal failure mode            | empirically: 2 interleaved tx conflict on 3.1.3; 2.6.5 needed ~8 concurrent tx |

There is **no `pytest.skip` capability gate on the decorator itself** — it is pure-Python and
works on both lines. The E2E test that _forces_ an interactive conflict probes
`client.begin()` and skips the interactive-only assertion on 2.6.x (adaptive-skip pattern),
while a buffered-path conflict test runs on both.

## Public API

```python
from surreal_orm_lite import retry_on_conflict, is_conflict_error, SurrealDbConflictError

@retry_on_conflict(max_retries=3, base_delay=0.05, max_delay=2.0, backoff_factor=2.0)
async def transfer(src_id: str, dst_id: str, amount: int) -> None:
    async with SurrealDBConnectionManager.transaction() as tx:
        src = await Account.objects(tx=tx).get(src_id)
        dst = await Account.objects(tx=tx).get(dst_id)
        await src.merge(tx=tx, balance=src.balance - amount)
        await dst.merge(tx=tx, balance=dst.balance + amount)
```

### `retry_on_conflict`

Signature (mirrors the full ORM exactly):

```python
def retry_on_conflict(
    max_retries: int = 3,
    base_delay: float = 0.05,
    max_delay: float = 2.0,
    backoff_factor: float = 2.0,
    jitter: bool = True,
) -> Callable[[F], F]: ...
```

- Decorates an **async** function. Total attempts = `max_retries + 1` (the first try plus
  `max_retries` retries).
- On each caught conflict (and only a conflict — see detection), sleeps
  `min(base_delay * backoff_factor**attempt, max_delay)`; with `jitter=True` the slept value is
  `delay * random.uniform(0.5, 1.0)` (anti-thundering-herd). `attempt` is 0-based so the first
  retry waits ~`base_delay`.
- A **non-conflict** exception propagates immediately (no retry).
- After `max_retries` retries still conflict, re-raises a `SurrealDbConflictError` wrapping the
  last error (message: `"Transaction conflict persisted after {max_retries} retries in
{func.__name__}: {last_error}"`).
- **Parameter validation at decoration time** (not call time): `max_retries < 0`,
  `base_delay <= 0`, `max_delay <= 0`, or `backoff_factor <= 0` raise `ValueError`. `jitter`
  added beyond the full ORM's signature so tests get deterministic backoff
  (`jitter=False`); default `True` keeps prod behaviour identical to the full ORM.
- Logs a `warning` per retry (`logging`, logger `surreal_orm_lite.concurrency`), like the full
  ORM.
- Preserves the wrapped function's identity via `functools.wraps`.

### `is_conflict_error(exc: BaseException) -> bool`

`True` when `exc` represents a **retryable** transaction conflict. Logic:

- `isinstance(exc, SurrealDbConflictError)` → `True`, else
- walk `exc` and its `__cause__` / `__context__` chain; for each, lower-case `str(...)` and
  match any signal substring.

Conflict signals (lower-case substring match):

```
"can be retried"            # SurrealDB's own retryability marker — primary, both DB lines
"transaction conflict"      # 3.1.3 wording
"read or write conflict"    # 2.6.5 wording
"write conflict"            # belt-and-suspenders
```

**Deliberately NARROWER than the full ORM**, which also matches `"failed transaction"` and bare
`"conflict"`. Those over-match: SurrealDB's non-retryable filler statement `"The query was not
executed due to a failed transaction"` contains `"failed transaction"`, so the full ORM's set
would classify a _non-retryable_ failure (e.g. a duplicate-key `AlreadyExists` inside a
transaction) as retryable and loop pointlessly. Anchoring on SurrealDB's explicit `"can be
retried"` marker is correct and was verified against the real 2.6.5 and 3.1.3 messages.

### `SurrealDbConflictError(SurrealDbError)`

New exception in `exceptions.py`, subclass of `SurrealDbError` (so existing `except
SurrealDbError` and `pytest.raises(SurrealDbError, match="rolled back")` keep working). Carries
the conflict message. Exported from the package root.

## Transaction-layer normalisation (`transaction.py`)

Goal: a conflict surfaces as `SurrealDbConflictError` on **every** path, so users and the
decorator see one type.

1. **`Transaction.raise_for_status`** — two changes:
   - **Root-cause selection fix (required).** Empirically, on a 3.x _buffered_ conflict **all**
     `ERR` statements carry `details.kind == "NotExecuted"`, including the real one
     (`"Cannot COMMIT: Transaction conflict… can be retried"`); the current selector therefore
     falls back to `errors[0]` (the generic filler) and the conflict message is lost. New
     selection order: (a) first ERR with `details.kind != "NotExecuted"` (unchanged — keeps the
     `AlreadyExists` test green), else (b) first ERR whose message is **not** the pure filler
     `"The query was not executed due to a failed transaction"`, else (c) `errors[0]`.
   - **Conflict typing.** If the surfaced message satisfies `is_conflict_error`, raise
     `SurrealDbConflictError(...)` instead of `SurrealDbError(...)`; the message keeps the
     existing `"Transaction failed and rolled back: …"` prefix so the `match="rolled back"`
     tests still pass.
2. **`InteractiveTransaction.commit` / `add` / `run_read`** — wrap the SDK call; if it raises and
   `is_conflict_error(raised)` is `True`, raise `SurrealDbConflictError(str(raised)) from
raised`; otherwise let the original propagate unchanged.

To avoid an import cycle (`concurrency` → `transaction`? no — `transaction` would import
`is_conflict_error` from `concurrency`), the small signal-matching predicate lives where both
can reach it without a cycle. **Decision:** put `is_conflict_error` and the signal list in
`concurrency.py`, and have `transaction.py` import it lazily _inside_ the methods (function-level
import), mirroring how the full ORM imports its conflict helper lazily inside the decorator.
`concurrency.py` imports only `exceptions` (no cycle).

## Error handling

- Decorating a non-coroutine, or other misuse → standard Python behaviour; the wrapper is async
  and will be awaited, so wrapping a sync function surfaces at call time (documented: async
  only, like the full ORM).
- Bad parameters → `ValueError` at decoration time.
- Non-conflict DB/SDK errors → propagate unchanged (the decorator re-raises immediately).
- Conflict after exhaustion → `SurrealDbConflictError` (the wrapper's "persisted after N
  retries" error, chained from the last underlying conflict via `from`).

## Deliberate scope decisions

- **No version column / no automatic OCC field.** "Optimistic concurrency" here = the
  retry-on-conflict loop over SurrealDB's native conflict detection (and the existing v0.11.0
  JSON-Patch `test` op for compare-and-set). We do **not** add a magic `version` field; that is
  not in the spec and SurrealDB's MVCC already provides the conflict signal.
- **Async-only decorator.** Matches the ORM (all DB I/O is async). No sync variant.
- **`jitter` is the only addition** to the full ORM's signature, purely for test determinism.
- **Narrow conflict signals** (above) — a documented, intentional divergence from the full ORM.
- Test-op (`test`) precondition failures from `patch()` are **not** retried — they are not
  retryable conflicts (no `"can be retried"` marker); retrying a failed precondition would loop.

## Acceptance criteria

1. `retry_on_conflict` retries exactly `max_retries` times on a conflict then re-raises
   `SurrealDbConflictError`; verified without a DB by monkeypatching `asyncio.sleep` and raising
   a conflict from the wrapped function (deterministic, `jitter=False`).
2. A wrapped function that conflicts once then succeeds returns the success value (one retry).
3. A non-conflict exception is **not** retried (propagates on the first raise).
4. Backoff sequence is `base_delay * backoff_factor**attempt` capped at `max_delay` (asserted on
   the monkeypatched sleep arguments, `jitter=False`).
5. Bad parameters raise `ValueError` at decoration time.
6. `is_conflict_error` returns `True` for the real 2.6.5 and 3.1.3 conflict messages and for
   `SurrealDbConflictError`; `False` for the non-retryable filler, an `AlreadyExists`-style
   message, and unrelated errors.
7. `raise_for_status` surfaces the conflict cause (not the filler) and raises
   `SurrealDbConflictError` on a conflict response; still raises the `AlreadyExists` root cause
   (existing test) and still raises plain `SurrealDbError` on a non-conflict failure.
8. **E2E**: a forced conflict raises `SurrealDbConflictError` on :8001; `retry_on_conflict`
   eventually succeeds when the competing writer stops. Buffered-path behaviour verified on
   :8002 (adaptive-skip for the interactive-only assertion).
9. Quality gates: `ruff format --check`, `ruff check`, `mypy src/` clean; coverage ≥ 70 %.
