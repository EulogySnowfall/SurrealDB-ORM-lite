# v0.13.0 — `SurrealFunc` & `server_values=` / `extra_vars=` — Design

- **Date**: 2026-07-22
- **Status**: Approved (design)
- **Target version**: 0.13.0
- **Roadmap**: Tier 1, Phase B — Server-side computation
- **SDK primitive**: none new — `client.query()` with a compiled `SET` clause (native SurrealQL
  functions evaluated server-side)
- **Constraint**: official SDK only (`surrealdb[pydantic]>=2.0.0,<3.0.0`); all SDK imports via
  `_sdk.py`; anything without a native SDK method goes through `client.query()`.

## Goal

Let a write evaluate values **on the server** instead of in Python: creation timestamps that
use the DB clock (`time::now()`), password hashes computed by the server
(`crypto::argon2::generate($password)`), server-generated identifiers (`rand::uuid::v7()`), …
v0.13.0 adds:

1. **`SurrealFunc(expression)`** — a marker wrapping a raw SurrealQL expression to be inlined
   (not bound) into the write statement, plus **`SurrealFunc.call(fn, *args)`**, an ergonomic
   builder (`SurrealFunc.call(SurrealTimeFunction.NOW)` → `SurrealFunc("time::now()")`).
2. **Curated function-name enums** — `SurrealFunction` (a `StrEnum` base) with
   `SurrealTimeFunction`, `SurrealMathFunction`, `SurrealStringFunction`,
   `SurrealArrayFunction`, `SurrealCryptoFunction`, `SurrealRandFunction`. Every member is
   **verified to resolve on both SurrealDB 2.6.5 and 3.1.3**; names that diverge between the
   lines (`rand::guid`, `type::is::*`) are deliberately excluded.
3. **`server_values=` / `extra_vars=` on `save()` and `merge()`** — `server_values` maps field
   names to `SurrealFunc`s; `extra_vars` binds additional query parameters the expressions can
   reference (`$password`), so user input stays parameterized.

```python
from surreal_orm_lite import SurrealFunc, SurrealCryptoFunction, SurrealTimeFunction

await player.save(server_values={"joined_at": SurrealFunc("time::now()")})
await user.save(
    server_values={"password_hash": SurrealFunc.call(SurrealCryptoFunction.ARGON2_GENERATE, "$password")},
    extra_vars={"password": raw_password},
)
await user.merge(plan="pro", server_values={"updated_at": SurrealFunc.call(SurrealTimeFunction.NOW)})
```

This is the lite re-implementation of the full ORM's `SurrealFunc` + `save(server_values=,
extra_vars=)` (full ORM: `surreal_orm/surreal_function.py`, `model_base.py::_build_set_clause`),
against the official SDK. The full ORM's enum catalog is incomplete/unverified; lite ships a
curated catalog verified against both server lines instead.

## SDK primitives used

- **`client.query(sql, vars)`** — the only path that can evaluate a server-side expression.
  The SDK's native `create()`/`merge()` send data as CBOR values, so a function would arrive
  as a literal string; it must be part of the query text instead.
- Empirical facts (probed on :8001 = 3.1.3 and :8002 = 2.6.5 before this design, identical on
  both):
  - `CREATE $rid CONTENT $data SET joined = time::now()` is a **parse error** on both lines
    (`CONTENT` and `SET` are exclusive) → the whole write must be compiled as one `SET` clause.
  - `CREATE $rid SET name = $n, joined = time::now()` works with `$rid` bound to a native
    `RecordID`, and returns the created row (default `RETURN AFTER`).
  - `UPDATE $rid SET age = $a, updated = time::now()` works and is a **partial** update (only
    the listed fields change) — the correct compilation target for `merge()`.
  - `CREATE <table> SET …` auto-generates the id on both lines.
  - `crypto::argon2::generate($pw)` / `::compare`, `crypto::bcrypt::*` exist on both lines.

## Capability dispatch — 2.6.x vs 3.x

**Identical on both DB lines — by design.** The feature compiles to plain SurrealQL (`CREATE …
SET` / `UPDATE … SET`) using only functions verified on both lines; there is no 3.x-only
primitive and **no `pytest.skip` capability gate**. The only behavioural split is the one
inherited from the transaction strategies (v0.9.0), not from this feature:

| Aspect                                  | SurrealDB 2.6.5 (buffered tx)                          | SurrealDB 3.1.3 (interactive tx on WS)         |
| --------------------------------------- | ------------------------------------------------------ | ---------------------------------------------- |
| `save`/`merge` + `server_values`, no tx | works, instance synced with returned row               | same                                           |
| Inside a transaction (`tx=`)            | statement buffered; instance **stale** for func fields | row applied at `add()` time (reads-see-writes) |
| `save(tx=)` with auto-generated id      | raises (existing v0.8.0 rule, unchanged)               | works                                          |

## Public API

### `SurrealFunc` (new module `functions.py`)

```python
class SurrealFunc:
    def __init__(self, expression: str) -> None: ...
    @classmethod
    def call(cls, fn: str | SurrealFunction, *args: str) -> "SurrealFunc": ...
```

- `expression` must be a non-empty string and may **not** contain `;` (statement terminator) —
  a footgun guard, **not** a security boundary (see Security model). Stored stripped.
  Violations raise `ValueError` at construction time.
- `call(fn, *args)` renders `f"{fn}({', '.join(args)})"` and wraps it: `fn` is a plain string
  or any `SurrealFunction` enum member (its value is the function name); each `arg` is a **raw
  SurrealQL fragment** (`"$password"`, a field name, a literal) under the same
  developer-controlled trust model as the expression itself.
- `__repr__` (`SurrealFunc('time::now()')`), `__eq__`/`__hash__` by expression (usable in sets
  and assertions).

### Function-name enums (`functions.py`)

`class SurrealFunction(StrEnum)` — empty base, exists so `isinstance`/typing can address "any
function enum" and users can define their own members. Curated subclasses (member → value; all
verified on 2.6.5 **and** 3.1.3):

- **`SurrealTimeFunction`**: NOW, CEIL, FLOOR, ROUND, GROUP, UNIX, DAY, MONTH, YEAR, HOUR,
  MINUTE, SECOND, WDAY, WEEK, YDAY, MIN, MAX (`time::now`, `time::ceil`, …)
- **`SurrealMathFunction`**: ABS, CEIL, FLOOR, ROUND, SQRT, POW, MEAN, MEDIAN, SUM, PRODUCT,
  MIN, MAX, FIXED, STDDEV, VARIANCE
- **`SurrealStringFunction`**: CONCAT, LOWERCASE, UPPERCASE, TRIM, LEN, SLUG, REPLACE, REVERSE,
  SPLIT, JOIN, STARTS_WITH, ENDS_WITH, CONTAINS, REPEAT
- **`SurrealArrayFunction`**: APPEND, CONCAT, ADD, COMPLEMENT, DISTINCT, LEN, REVERSE, SORT,
  FLATTEN, FIRST, LAST, MIN, MAX
- **`SurrealCryptoFunction`**: ARGON2_GENERATE, ARGON2_COMPARE, BCRYPT_GENERATE, BCRYPT_COMPARE,
  SHA256, SHA512, MD5 (`crypto::argon2::generate`, …)
- **`SurrealRandFunction`**: RAND (`rand`), UUID, UUID_V4, UUID_V7, ULID, BOOL, FLOAT, INT,
  STRING, TIME, ENUM (`rand::uuid`, `rand::uuid::v4`, …)

Excluded because they diverge between server lines: `rand::guid` (2.6-only), `type::is::*`
(2.6 spelling; 3.x renamed to `type::is_*`). Users needing a divergent or uncatalogued function
pass its name as a string or use `SurrealFunc("…")` directly — the enums are DX, not a gate.

### `save()` / `merge()` extensions (`model_base.py`)

```python
async def save(self, tx=None, server_values: dict[str, SurrealFunc] | None = None,
               extra_vars: dict[str, Any] | None = None) -> Self: ...
async def merge(self, tx=None, server_values: dict[str, SurrealFunc] | None = None,
                extra_vars: dict[str, Any] | None = None, **data: Any) -> Any: ...
```

- Without `server_values`/`extra_vars` both methods behave **exactly** as today (native SDK
  `create()`/`merge()` path untouched).
- With `server_values`, the write routes through `client.query()`:
  - `save()` + explicit id → `CREATE $rid SET <clause>;` (`$rid` bound to the `RecordID`);
    auto-id → `CREATE <table> SET <clause>;` (table from `get_table_name()`, validated).
  - `merge()` → `UPDATE $rid SET <clause>;` (partial: only listed fields change).
- **Clause compilation**: `merged = {**data, **server_values}` (a server value overrides a
  same-named model/merge field). For each key: `SurrealFunc` → inlined raw (`key = expr`);
  anything else → bound (`key = $_sv_<key>`). Keys validated as plain identifiers
  (`^[a-zA-Z_][a-zA-Z0-9_]*$`). `save`/`merge` validate — **before** compilation, since the
  merged dict no longer distinguishes origins — that every `server_values` value is a
  `SurrealFunc` (`TypeError` otherwise).
- **`extra_vars`** are merged into the query bindings after compilation; a key that collides
  with an internal binding (`rid`, any `_sv_*`) raises `ValueError`. `extra_vars` without
  `server_values` raises `ValueError` (nothing can reference them).
- **Self-sync**: non-tx and interactive-tx calls apply the returned row to `self`
  (`_apply_record`, statement default `RETURN AFTER`) — so the server-computed values are
  immediately visible on the instance. `merge()`'s SET path therefore does **not** issue the
  separate `refresh()` round-trip the MERGE path uses. In a buffered tx the result is unknown
  until commit: literal `data` values are applied to `self`, func fields stay stale
  (documented, same caveat as `merge(tx=)` today).
- **Signals**: unchanged envelopes. `save()` emits `pre_save`/`around_save`/`post_save` via the
  existing `_save_with_signals`; `merge()` emits `pre_update`/`around_update`/`post_update`
  with `update_fields = list(merged.keys())` (func fields included). Tx deferral rules
  unchanged.
- **Error normalisation**: a `CREATE` on an existing id raises the SDK's `ServerError`; the
  "already exists" case is normalised to `SurrealDbError` exactly like `_do_save` does today.
  Other server errors (unknown function, wrong args) propagate as SDK exceptions, per the
  existing convention.
- `server_values` / `extra_vars` join `tx` as reserved keyword names for `merge()` (a model
  field with one of those names can't be merged by keyword — documented, no realistic column
  is named that).

### Compilation helper (`utils.py`)

```python
def build_set_clause(merged: Mapping[str, Any], param_prefix: str = "_sv_") -> tuple[str, dict[str, Any]]
def merge_extra_vars(variables: dict[str, Any], extra_vars: Mapping[str, Any] | None) -> dict[str, Any]
```

Pure functions (unit-testable without a DB): `build_set_clause` validates keys, inlines
`SurrealFunc`s, binds everything else; `merge_extra_vars` enforces the collision rule.
`utils.py` imports `SurrealFunc` from `functions.py` (which imports nothing from the package —
no cycle).

## Security model

- **The injection boundary is parameter binding, unchanged**: every regular field value and
  every `extra_vars` value is bound (`$_sv_<field>` / `$<name>`), never string-interpolated. A
  hostile _value_ cannot escape.
- **`SurrealFunc` expressions are trusted developer input**, inlined by definition. Docstrings
  and README state: never build a `SurrealFunc` from user input; route user input through
  `extra_vars`. The `;` rejection is a guard against accidental statement chaining, not a
  sanitizer.
- `server_values` keys and the auto-id table name are validated identifiers before
  interpolation (same discipline as the v0.11.0 atomic helpers).

## Deliberate scope decisions

- **`save()` + `merge()` only** (per roadmap spec and user decision 2026-07-22). `update()`,
  `upsert()`, `QuerySet.bulk_update()` are not extended in v0.13.0; `upsert()`-via-SET would
  silently lose its native full-REPLACE semantics.
- **Enums are curated, not exhaustive** (user decision 2026-07-22: ship enums; lite curates to
  dual-line-verified names). A member per function verified by an E2E test on both ports.
- **No `DEFINE FIELD … VALUE` here** — that is v0.14.0 (Computed Fields). v0.13.0 is per-write
  server evaluation only.
- **No signature drift**: parameter names (`server_values`, `extra_vars`) mirror the full ORM.

## Acceptance criteria

1. `SurrealFunc`: empty/`;`-containing expression → `ValueError`; `call()` renders
   `fn(arg, …)` from both a string and an enum member; `repr`/`eq`/`hash` behave.
2. `build_set_clause`: funcs inlined, other values bound as `$_sv_<key>`; a `server_values`
   entry overrides a same-named data field; invalid key → `ValueError`; non-`SurrealFunc` in
   `server_values` (via `save`/`merge` validation) → `TypeError`. Unit-tested without a DB,
   including an injection-shaped _value_ remaining a bound parameter.
3. `merge_extra_vars`: collision with `rid`/`_sv_*` → `ValueError` (message lists offenders);
   `extra_vars` without `server_values` → `ValueError` from `save`/`merge`.
4. **E2E on :8001 and :8002** — `save(server_values={"joined_at": …time::now…})` with explicit
   id: the stored and instance value is a server `datetime`, not the literal string; creating
   the same id twice raises `SurrealDbError` ("already exists"). Auto-id save works non-tx.
5. **E2E both ports** — `save(server_values=…ARGON2_GENERATE…, extra_vars={"password": …})`:
   stored hash verifies with `crypto::argon2::compare` server-side; the raw password appears
   nowhere in the stored record.
6. **E2E both ports** — `merge(plan="pro", server_values={"updated_at": …})`: listed fields
   updated (bound + computed), unlisted fields preserved, instance synced;
   `pre_update`/`post_update` fire with `update_fields` containing both keys.
7. **Transactions** — buffered (:8002 or HTTP): statement deferred, DB state correct after
   commit, rollback leaves no write, instance stale for func fields; interactive (:8001 WS):
   row applied at `add()` time; auto-id + buffered tx raises (unchanged rule). Adaptive-skip
   only where a port lacks the strategy (existing pattern).
8. **Enum catalog E2E** — parametrized test invokes every enum member (with sample args) via
   `RETURN <expr>` on both ports; all resolve.
9. Quality gates: `ruff format --check`, `ruff check`, `mypy src/` clean; coverage ≥ 70 %.
