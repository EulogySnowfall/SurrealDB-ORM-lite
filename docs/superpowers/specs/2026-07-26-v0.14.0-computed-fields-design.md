# v0.14.0 — Computed Fields (`Computed[...]` → `DEFINE FIELD … VALUE`) — Design

- **Date**: 2026-07-26
- **Status**: Approved (design)
- **Target version**: 0.14.0
- **Roadmap**: Tier 1, Phase B — Server-side computation
- **SDK primitive**: none new — `client.query()` running the DDL statement
  `DEFINE FIELD … VALUE <expr>` (SurrealQL DDL, no native SDK method exists)
- **Constraint**: official SDK only (`surrealdb[pydantic]>=2.0.0,<3.0.0`); all SDK imports via
  `_sdk.py`; anything without a native SDK method goes through `client.query()`.

## Goal

Declare a field whose value SurrealDB **derives from other fields on every write**, instead of
Python computing it and shipping it over the wire. Where v0.13.0 evaluates an expression **per
write** (`save(server_values={"joined_at": SurrealFunc("time::now()")})`), v0.14.0 attaches the
expression to the **schema**: it is defined once and then applies to every `CREATE`, `UPDATE`,
`MERGE`, `UPSERT` and `PATCH` on that table, no matter who issues it — the ORM, another
service, or the SurrealDB CLI.

```python
from surreal_orm_lite import BaseSurrealModel, Computed, SurrealFunc

class Player(BaseSurrealModel):
    id: str
    first_name: str
    last_name: str
    full_name: Computed[str] = Computed("string::concat(first_name, ' ', last_name)")
    slug: Computed[str] = Computed(SurrealFunc("string::slug(full_name)"))

await Player.define_computed_fields()        # DEFINE FIELD OVERWRITE … VALUE …
p = await Player(id="ada", first_name="Ada", last_name="Lovelace").save()
p.full_name                                  # "Ada Lovelace" — computed by the server
```

v0.14.0 ships three things:

1. **`Computed`** — a dual-use class: `Computed[T]` as an annotation (resolves to
   `Annotated[T | None, marker]`, default `None`) and `Computed("expr")` as the field default
   carrying the SurrealQL expression.
2. **DDL emission/application** — `Model.computed_field_ddl()` (pure, returns the statements)
   and `await Model.define_computed_fields()` (runs them, `tx=` supported).
3. **Write exclusion + guards** — computed fields never appear in a write payload, and naming
   one in `merge()`, `QuerySet.bulk_update()` or an `atomic_*` helper raises `ValueError`.

This is the lite re-implementation of the full ORM's `Computed` (full ORM:
`surreal_orm/fields/computed.py` + `model_base.py::get_server_fields`/`define_table`), against
the official SDK. The full ORM reaches it through a whole migrations/introspection subsystem
(`ModelIntrospector`, `AddField`, `CreateTable`); lite ships only the narrow computed-field
emitter — general schema sync stays v0.30.0 (introspection) and v0.37.0 (migrations).

## SDK primitives used

- **`client.query(sql)`** — the only path to DDL; the SDK exposes no `define_field()` method.
- Empirical facts, probed on :8001 (3.1.3) and :8002 (2.6.5) before this design. **Every
  result below was byte-identical on both lines** unless the row says otherwise:
  - `DEFINE FIELD full_name ON Person VALUE string::concat(first_name, ' ', last_name);` works
    on a **schemaless** table with no `TYPE` clause; the server infers an optional type.
  - `DEFINE FIELD OVERWRITE …` and `DEFINE FIELD IF NOT EXISTS …` are both accepted.
  - `TYPE option<string> VALUE …` and `VALUE … READONLY` are both accepted (neither is used —
    see _Deliberate scope decisions_).
  - The value is recomputed on `CREATE`, `UPDATE … SET`, `UPDATE … MERGE`, `UPSERT … CONTENT`
    and `UPDATE … PATCH`.
  - **A client-sent value for the field is discarded.** Creating `Person:c` with
    `first_name: 'Cy'`, `last_name: 'N'` and an explicit `full_name: 'HACKED'` stores
    `full_name = 'Cy N'`. Sending `NONE` likewise loses to the expression.
  - The DDL runs inside `BEGIN TRANSACTION; … COMMIT TRANSACTION;`.
  - Computed fields evaluate in **alphabetical field-name order**, not declaration order:
    `subtotal` → `total` resolves, but `z_sub` → `a_total` fails with
    `Cannot perform multiplication with 'none' and 'int'`.
  - A `$param` bound on the DDL `query()` call is **not** captured into the definition (the
    expression must be self-contained).
  - `INFO FOR TABLE` renders the inferred type as `none | string` on 3.1.3 and
    `option<string>` on 2.6.5 — cosmetic, and nothing in v0.14.0 parses it.
  - **The one divergence**: an invalid expression raises `ValidationError` on 3.1.3 and
    `InternalError` on 2.6.5. Both subclass `ServerError`.

## Capability dispatch — 2.6.x vs 3.x

**Identical on both DB lines — no capability probe, no `pytest.skip` gate anywhere in this
feature.** `DEFINE FIELD … VALUE` is not a 3.x primitive; the syntax, the recompute triggers
and the precedence over client-sent data all matched exactly across the two lines.

The single divergence is an **exception type**, normalised by the ORM so callers see one error:

| Aspect                                           | SurrealDB 2.6.5            | SurrealDB 3.1.3               |
| ------------------------------------------------ | -------------------------- | ----------------------------- |
| `DEFINE FIELD … VALUE` syntax & recompute        | works                      | same                          |
| Client-sent value for a computed field           | discarded, expression wins | same                          |
| Alphabetical evaluation order of computed fields | same                       | same                          |
| Invalid expression, raw SDK exception            | `InternalError`            | `ValidationError`             |
| Invalid expression **through the ORM**           | `SurrealDbError`           | `SurrealDbError` — normalised |

This mirrors the v0.7.0 normalisations (missing table: silent on 2.6.x, `NotFoundError` on 3.x)
and the v0.12.0 conflict typing: catch the common `ServerError` base, re-raise one ORM type.

`define_computed_fields(tx=)` inherits the v0.9.0 transaction split unchanged — interactive on
WS + 3.x, buffered otherwise. Nothing feature-specific is added there.

## Public API

### `Computed` (`functions.py`)

Joins `SurrealFunc` in the existing server-side-computation module (user decision 2026-07-26);
`Computed` stores its expression **as a `SurrealFunc`**, so the two share one validation path
and one trust model.

```python
class Computed:
    def __class_getitem__(cls, inner: type) -> type: ...        # Computed[str]
    def __new__(cls, expression: str | SurrealFunc) -> "_ComputedDefault": ...
```

- **`Computed[T]`** → `Annotated[T | None, _ComputedMarker(T)]`. The field is nullable with
  default `None`, so an instance is constructible before the server has ever computed it, and
  a row that predates the `DEFINE FIELD` still validates.
- **`Computed("expr")`** → a `_ComputedDefault` sentinel. `BaseSurrealModel.__init_subclass__`
  (new) collects sentinels from the class body into `__surreal_computed__` and replaces each
  with `None` before Pydantic builds the model. Inherited computed fields are merged from base
  classes, subclass definitions winning.
- The expression accepts a `str` or a `SurrealFunc`; either way it is normalised through
  `SurrealFunc`, inheriting its rules: non-empty, stripped, no `;`. Violations raise
  `ValueError`/`TypeError` at **class-definition time**.
- `_ComputedDefault.__repr__` → `Computed("string::concat(first_name, ' ', last_name)")`.

The plain form `full_name: str | None = Computed("…")` also works (detection keys off the
sentinel default, not the annotation) and is covered by a test, but `Computed[T]` is the
documented spelling — it is self-describing at the point of declaration.

### Model surface (`model_base.py`)

```python
@classmethod
def get_computed_fields(cls) -> dict[str, str]: ...                    # name -> expression
@classmethod
def computed_field_ddl(cls, overwrite: bool = True) -> list[str]: ...  # pure, no I/O
@classmethod
async def define_computed_fields(cls, overwrite: bool = True,
                                 tx: Transaction | None = None) -> list[str]: ...
```

- `get_computed_fields()` returns a **copy**, ordered by declaration; `{}` for a model with
  none. It is the single source of truth every write path consults.
- `computed_field_ddl()` renders one statement per computed field:
  `DEFINE FIELD OVERWRITE <name> ON <Table> VALUE <expr>;`. With `overwrite=False`:
  `DEFINE FIELD IF NOT EXISTS <name> ON <Table> VALUE <expr>;`. Field name and table name are
  validated as plain identifiers before interpolation (same discipline as the v0.11.0 atomic
  helpers). Pure and unit-testable with no database.
- `define_computed_fields()` executes them **one statement per `query()` call**, so a failure
  names the offending field, and returns the list of statements run (`[]` if the model has no
  computed fields — a no-op, not an error). A `ServerError` is re-raised as `SurrealDbError`
  carrying the statement text. With `tx=`, statements go through `tx.add()`.

**Default `overwrite=True`** (user decision 2026-07-26): the model is the source of truth, so
re-running at application startup converges the database to the code. Editing an expression in
Python and redeploying takes effect. `overwrite=False` is the opt-in for "never touch what is
already defined".

### Write exclusion

`BaseSurrealModel._write_payload() -> dict[str, Any]` replaces the scattered
`self.model_dump(exclude={"id"})` calls in `_do_save`, `_do_save_server`, `_do_upsert`,
`update()`, and `QuerySet.bulk_create()`. It dumps the model excluding `id` **and** every
computed field. (`bulk_create` re-adds `id` afterwards, as it does today.)

Excluding matters even though the server discards client-sent values anyway:

- on a **schemafull** table, a `None` for a non-optional field fails `TYPE` validation;
- if `define_computed_fields()` was never run, the field is an ordinary column and the `None`
  would actually **land**, nulling stored data;
- it keeps the wire payload honest about who owns the value.

### Write guards

Naming a computed field in one of these raises `ValueError` naming the field and the model:

- `model.merge(full_name="x")`
- `QuerySet.bulk_update(full_name="x")`
- all seven `atomic_*` helpers (`atomic_append`, `atomic_remove`, `atomic_set_add`,
  `atomic_increment`, and the three `*_many` variants) — one check in the shared
  `_atomic_update`, so it cannot drift between them

Rationale (user decision 2026-07-26): the write is silently discarded server-side, so raising
converts an invisible no-op into a clear error at the call site.

Deliberately **not** guarded:

- `patch()` / `QuerySet.patch()` — JSON Pointers are opaque paths, not field names; the server
  recomputes regardless. Documented, not enforced.
- Python attribute assignment (`p.full_name = "x"`) — a local attribute write that the next
  read or write resets. Fighting Pydantic here would cost more than it buys.

### Reads

No change needed. A computed field is a declared nullable model field, so `from_db()` and
`_apply_record()` already hydrate it from the returned row, and it is filterable/orderable in
a `QuerySet` like any column (verified server-side in the probe).

## Security model

- **Expressions are trusted developer input, inlined into DDL by definition** — identical to
  `SurrealFunc` (v0.13.0). They live in a class body, which is source code, not runtime data.
  The docs state plainly: never build a `Computed` expression from user input.
- Because a `DEFINE FIELD` expression cannot reference bound parameters at all (probed), there
  is no `extra_vars` analogue and no ambiguity about where the injection boundary sits.
- Field names and the table name are validated identifiers before interpolation.
- The `;` rejection inherited from `SurrealFunc` guards against accidental statement chaining;
  it is not a sanitizer.
- Worth stating in the README: a computed field is a **server-enforced** invariant. A client
  that sends `full_name: "HACKED"` cannot override it (probed on both lines) — that is a
  security property `server_values=` alone does not give you.

## Deliberate scope decisions

- **No `TYPE` clause emitted.** The server already infers an optional type, and a
  Python→SurrealQL type map is v0.23.0's job (rich field types). Emitting a half-built one now
  would be a compatibility liability.
- **No `READONLY`, `ASSERT`, `PERMISSIONS`, or `DEFAULT`** — general `DEFINE FIELD` support is
  v0.30.0+ territory. v0.14.0 emits exactly the `VALUE` clause the roadmap names.
- **No `DEFINE TABLE`, no schemafull mode, no removal helper.** Tests and the notebook drop
  tables with `REMOVE TABLE`.
- **No automatic DDL on save.** Applying schema is an explicit, deliberate call; an implicit
  DDL round-trip inside the write path would be a surprise and a performance trap.
- **No dependency-order sorting of emitted statements.** The evaluation order is the
  _server's_ (alphabetical, at write time), not the definition order — reordering the DDL
  would not change it. Documented as a caveat instead.
- **`update_or_create()` / `get_or_create()` need no changes**: both build a model and delegate
  to `save()`/`merge()`, which are already covered.

## Acceptance criteria

1. `Computed[str]` produces a nullable field defaulting to `None`; a model with computed
   fields is constructible without supplying them; `Computed("")`, `Computed("a; b")` and
   `Computed(123)` raise at class-definition time.
2. `get_computed_fields()` returns `{name: expression}` in declaration order, `{}` for a plain
   model, merges inherited fields, and returns a copy (mutating it does not corrupt the class).
   Accepts both `Computed(str)` and `Computed(SurrealFunc)`; the plain-annotation form works.
3. `computed_field_ddl()` renders `DEFINE FIELD OVERWRITE <f> ON <T> VALUE <e>;` by default and
   `IF NOT EXISTS` with `overwrite=False`; `[]` for a model with none. Unit-tested with no DB.
4. **E2E on :8001 and :8002** — after `define_computed_fields()`, `save()` stores and hydrates
   the computed value; the field is absent from the payload the ORM sends yet present on the
   instance afterwards.
5. **E2E both ports** — the value is recomputed by `merge()`, `update()`, `upsert()` and
   `patch()`; a `QuerySet` can `filter()` and `order_by()` on it.
6. **E2E both ports, security** — a record created with a hostile explicit value for the
   computed field (via `raw_query`, bypassing the ORM's exclusion) stores the **expression's**
   result, not the supplied one.
7. **E2E both ports** — `define_computed_fields()` is idempotent (re-running converges); with
   an edited expression and `overwrite=True` the new expression takes effect, and with
   `overwrite=False` the original definition survives.
8. **E2E both ports** — an invalid expression raises `SurrealDbError` (not the raw
   `ValidationError`/`InternalError` divergence), and the message names the statement.
9. `merge()`, `bulk_update()` and each `atomic_*` helper raise `ValueError` naming a computed
   field; a model with no computed fields is unaffected on every path.
10. **E2E both ports** — `define_computed_fields(tx=tx)` works on the buffered (:8002) and
    interactive (:8001 WS) strategies; a rolled-back transaction leaves no definition.
11. Quality gates: `ruff format --check`, `ruff check` (src **and** tests), `mypy src/` clean;
    coverage ≥ 70 %.
