# v0.14.3 — Correctness fixes from issue #156 — Design

- **Date**: 2026-08-21
- **Status**: Approved (design)
- **Target version**: 0.14.3
- **Roadmap**: none — a correctness release between v0.14.x and the planned v0.15.0
  (`call_function()`), which keeps its slot.
- **Source**: [issue #156](https://github.com/EulogySnowfall/SurrealDB-ORM-lite/issues/156),
  seven findings, all reproduced against live SurrealDB 3.2.4 **and** 2.6.5 before any code was
  written (see the validation comment on the issue).
- **SDK primitive**: none new. The two behavioural fixes (#4, #7) use SurrealQL that is already
  supported on both lines — `UPSERT … RETURN $before, $after` and `->edge->?.*` — through
  `client.query()`.
- **Constraint**: official SDK only; all SDK imports via `_sdk.py`.

## Goal

Close the seven findings without breaking any documented behaviour. Two of them
(#1, #6) silently corrupt results or stored data, so they set the tone of the release: the ORM
must never quietly return the wrong rows or write a field the model does not declare.

The version is a **patch** (0.14.3) rather than a minor, even though it introduces one new public
symbol (`Var`), because v0.15.0 is already committed to `call_function()` on the roadmap and
every change here is additive or a bug fix. No documented behaviour is removed.

## The seven fixes

### 1. `first()` must not mutate the queryset — High

`first()` assigned `self._limit = 1` and never restored it, so any reuse of the queryset stayed
capped at one row. `exists()` already had the right shape (save → `try` → restore in `finally`);
`first()` adopts it verbatim. Behavioural contract: **a terminal operation never changes the
queryset it was called on.**

### 2. Literal strings starting with `$` — High

`filter(name="$admin")` compiled to `name = $admin`, an unbound variable reference: no match, no
error. A literal that is not variable-shaped (`"$50 bill"`) raised `ValueError` instead.

The `$`-prefix convention is documented and stays (this is a patch release), but it gains the two
things it lacked:

- **`Var("name")`** — an explicit, unambiguous variable reference, the shape new code should use.
  Lives in `functions.py` next to `SurrealFunc`, exported from the package root.
- **`"$$literal"`** — a `$$` prefix escapes to a single `$`, so `filter(name="$$admin")` matches
  the literal `"$admin"`. This is the only way to express such a literal today.

A `DeprecationWarning` on the bare `"$name"` form points at `Var(...)`, so the default can be
flipped in v0.15.0 (strings always literal) without surprising anyone. The flip is recorded on
the roadmap, not performed here.

### 3. `remove_quotes_for_variables` must not touch user SQL — Medium

The regex rewrote `'$word'` → `$word` **anywhere** in the query text, including inside string
literals the caller wrote. The fix is scoping, not a smarter regex: user-authored SurrealQL
(`raw_query`, `objects().query()`) is sent **verbatim** — the caller owns that string and is
already expected to bind variables themselves. The helper stays on the ORM-compiled paths, where
the text is machine-generated and no user data ever reaches it (every value is bound).

### 4. `created` on upsert — Medium

`_do_upsert` reported `created=True` unconditionally, so the `post_save` signal lied on every
update. `UPSERT <rid> CONTENT $data RETURN $before AS before, $after AS after` returns both
states in **one** round-trip, on 2.6.5 and 3.2.4 alike (verified): `created = before is None`,
and `after` syncs the instance exactly as the native call did. No extra query, no signal payload
change — the flag simply becomes true.

REPLACE semantics are unchanged and remain documented: `upsert()` still fully replaces the row.

### 5. Multi-statement raw queries — Low

The SDK returns only the **first** statement's result set for a multi-statement query, silently.
`raw_query()` warns (`UserWarning`) when it is handed more than one statement, pointing at one
call per statement or `transaction()`. The detection is quote- and comment-aware so a `;` inside
a string literal does not trip it.

### 6. `update_or_create` / `get_or_create` and undeclared keys — High (raised from Medium)

The reported cause was wrong, and the real one is worse: keys absent from the model are dropped
by Pydantic on the **create** path but written straight to the database by `merge()` on the
**update** path. The same call therefore produces two different stored schemas depending on
whether the row happened to exist.

Fix: `_writable_payload` rejects undeclared keys with a `SurrealDbError` naming them — on both
paths, before any write. Silently dropping them would have been the other consistent option, but
a caller who passes `defaults={"nmae": …}` wants to hear about the typo, not lose the value.
Models that opt into extra fields (`model_config = ConfigDict(extra="allow")`) keep them on both
paths, which is the same rule stated once instead of two accidents.

### 7. `get_related` round-trips — Low

With `model_class=`, the traversal fetched RecordIDs and then issued a second
`SELECT * FROM $ids`. `SELECT VALUE ->edge->?.* FROM ONLY <thing>` returns the full records in
one query, identically on both DB lines (verified). The two-step path stays as a fallback for
results that are not RecordIDs, and the no-`model_class` call is unchanged (it was already one
query).

## 2.6.x vs 3.x

**Identical on both lines.** Every fix was reproduced and then verified on 3.2.4 *and* 2.6.5; the
two new SurrealQL forms (`RETURN $before/$after`, `->edge->?.*`) behave the same on each. No
capability probe, no adaptive skip, one new row in the README behaviour table saying exactly
that.

## Acceptance criteria

1. A queryset reused after `first()` returns all its rows; `_limit` is unchanged afterwards.
2. `filter(name="$$admin")` matches the row whose name is `"$admin"`; `Var("x")` compiles to a
   `$x` reference; the bare `"$x"` form still works and warns once.
3. `raw_query("SELECT * FROM U WHERE name = '$admin';")` returns the matching row.
4. `post_save` receives `created=False` when `upsert()` replaced an existing record, `True` when
   it created one — in one round-trip.
5. `raw_query` warns on two statements, stays silent on one containing `;` inside a string.
6. `update_or_create(defaults={"nope": 1}, …)` raises `SurrealDbError` on both the create and the
   update path; nothing named `nope` reaches the database. An `extra="allow"` model keeps it.
7. `get_related(..., model_class=X)` issues a single query and returns the same models as before.
8. All gates: both DB lines green, `ruff`, `mypy src/`, coverage ≥ 70 %.
