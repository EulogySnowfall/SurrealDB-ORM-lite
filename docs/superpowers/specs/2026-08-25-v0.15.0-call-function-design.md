# v0.15.0 — `call_function()` (custom `fn::` stored functions) — Design

- **Date**: 2026-08-25
- **Status**: Approved (design)
- **Target version**: 0.15.0
- **Roadmap**: Tier 1, Phase B — Core write-path / server-side computation
- **SDK primitive**: none — the installed SDK 2.0.0 exposes **no `run()` / `call()` method**
  (verified: `AsyncWsSurrealConnection` has no such attribute). The call goes through
  `client.query()` running a SurrealQL function-call statement.
- **Constraint**: official SDK only (`surrealdb[pydantic]>=2.0.0,<3.0.0`); all SDK imports via
  `_sdk.py`; anything without a native SDK method goes through `client.query()`.

## Goal

Invoke a custom server-side function declared with `DEFINE FUNCTION fn::…` and get its return
value back in Python, with **arguments bound as query parameters** and **SDK errors wrapped in
the ORM's exception hierarchy**.

```python
from surreal_orm_lite import SurrealDBConnectionManager

# positional — SurrealQL's own calling convention
acquired = await SurrealDBConnectionManager.call_function(
    "fn::acquire_lock", [table_id, pod_id, 30],
)

# named — argument order resolved from the function's declared signature
acquired = await SurrealDBConnectionManager.call_function(
    "fn::acquire_lock",
    params={"table_id": table_id, "pod_id": pod_id, "ttl": 30},
)

# typed return value
class LockResult(BaseModel):
    acquired: bool
    expires_at: datetime

lock = await SurrealDBConnectionManager.call_function(
    "fn::acquire_lock", [table_id, pod_id, 30], return_type=LockResult,
)
```

v0.15.0 ships four things:

1. **`SurrealDBConnectionManager.call_function()`** — the entry point named by the roadmap.
2. **Named-argument resolution** — `params={...}` ordered against the signature declared in
   `INFO FOR DB`, cached per namespace/database.
3. **`BaseSurrealModel.call_function()`** — a thin classmethod delegating to the manager
   (parity with the full ORM's `Model.call_function`).
4. **`tx=` support** — a stored function called inside `async with transaction()` runs
   **inside** that transaction, on both DB lines.

This is the lite re-implementation of the full ORM's `call_function`
(`surreal_orm/connection_manager.py::call_function` + `model_base.py::call_function`), which
delegates to its custom SDK's `client.call()`. The official SDK has no equivalent, so lite
builds the statement itself — which is what makes the argument-binding and transaction
semantics below the ORM's responsibility rather than the SDK's.

**Out of scope, deliberately**: a `define_function()` DDL helper. Declaring a function is DDL
and belongs in the `schema.py` module that the roadmap opens at **v0.31.0** (`DEFINE EVENT`);
v0.15.0 is about _calling_, not _declaring_. A roadmap row is added for it (see _Doc updates_).
Until then a function is declared the way users already declare one:
`await client.query("DEFINE FUNCTION fn::… { … };")`.

## SDK primitives used

- **`client.query(sql, vars)`** — the only path; there is no `run()`/`call()` in SDK 2.0.0.
- **`Transaction.add(sql, vars)`** (v0.8.0/v0.9.0) — routes the call through an open
  transaction, buffered or interactive.

### Empirical facts, probed on :8001 (3.2.4), :8002 (2.6.5) and :8003 (3.1.5)

Every result below was **identical on all three servers** unless the row says otherwise.

- `RETURN fn::greet($a0);` with bound vars returns the function's value. Arguments are
  positional; **SurrealQL has no named function arguments**.
- The **bare call form** `fn::greet($a0);` (no `RETURN`) returns the same value.
- Nested namespaces work: `fn::billing::total($a0)`.
- Zero-argument functions work: `fn::noargs();`.
- A function returning `NONE` yields Python `None`.
- `INFO FOR DB` returns a `functions` dict keyed by the name **without** the `fn::` prefix,
  whose value is the full `DEFINE FUNCTION` text including the parameter list:
  `"greet": "DEFINE FUNCTION fn::greet($name: string, $times: int) { … } PERMISSIONS FULL"`.
  (2.6.5 keeps a trailing `;` inside the body; the parameter list is byte-identical.)
- A missing function raises the SDK's `InternalError`. **The message differs by line**:
  3.x says `Function 'fn::x' not found: The function 'fn::x' does not exist`, 2.6.x says
  `The function 'fn::x' does not exist`. Both contain `does not exist` — tests assert on the
  ORM's exception type, never on the server's wording.
- Wrong arity raises `InternalError: Incorrect arguments for function fn::greet(). …`
  (identical wording on both lines).

### ⚠️ `RETURN` aborts a buffered transaction — the finding that shapes this design

Inside a `BEGIN … COMMIT` batch, a `RETURN` statement **terminates the transaction early and
silently**. Probed with `BEGIN; RETURN fn::bump($v); CREATE marker:m1 …; COMMIT;`:

| Server | Statements reported                | `marker:m1` created? |
| ------ | ---------------------------------- | -------------------- |
| 3.2.4  | 4, all `status: OK`                | **No**               |
| 2.6.5  | 2 (the `CREATE` vanished entirely) | **No**               |

The subsequent write is reported as successful and never happens — silent data loss, on both
lines. The **bare call form has no such effect**: with `BEGIN; fn::bump($v); CREATE marker:m1 …;
COMMIT;` the function runs, the value is still reported in the statement result, _and_ the
following statement executes.

**Therefore the ORM emits the bare call form everywhere** — outside a transaction, in an
interactive transaction, and in a buffered one. One statement shape, no context-dependent
branching, and no way for a `call_function()` to silently truncate a user's transaction.

## Capability dispatch (3.x vs 2.6.x)

The call itself is **identical on both lines** — no probe, no degradation. The only divergence
is the one already contracted by v0.9.0 transactions:

| Context                        | SurrealDB 2.6.x (buffered)                                                                                                | SurrealDB 3.x + WS (interactive)                           |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `call_function(...)` (no `tx`) | runs immediately, returns the value                                                                                       | same                                                       |
| `call_function(..., tx=tx)`    | queued; executes atomically at commit; **returns `None`**                                                                 | executes immediately inside the txn; **returns the value** |
| `params=` inside a `tx`        | signature read runs on the client **outside** the transaction, so it works even though buffered transactions forbid reads | same                                                       |

`return_type=` combined with a buffered `tx=` is a contradiction (there is no value yet to
coerce): it raises `ValueError` rather than silently returning `None`.

## Public API

```python
# connection_manager.py
@classmethod
async def call_function(
    cls,
    function: str,
    args: Sequence[Any] | None = None,
    *,
    params: Mapping[str, Any] | None = None,
    return_type: Any = None,
    tx: Transaction | None = None,
) -> Any: ...

# model_base.py — delegates, identical signature minus `cls` semantics
@classmethod
async def call_function(cls, function, args=None, *, params=None, return_type=None, tx=None) -> Any: ...
```

**`function`** — `"fn::acquire_lock"` or `"acquire_lock"`; the `fn::` prefix is added when
absent. The name is **interpolated into the statement**, because SurrealQL does not accept a
`$var` in call position. It is therefore validated first: after stripping `fn::`, it must be
one or more `[A-Za-z_][A-Za-z0-9_]*` segments joined by `::`. Anything else raises
`ValueError`. **Arguments are never interpolated** — always bound as `$_fnarg0`, `$_fnarg1`, ….

**`args` / `params`** — mutually exclusive; passing both raises `ValueError`. `args` is a
sequence in declaration order. `params` is a mapping resolved against the declared signature:

- The signature is read once via `INFO FOR DB`, parsed to an ordered tuple of parameter names,
  and cached under `(namespace, database, function)`.
- An unknown key, or a missing one, raises `ValueError` naming the expected parameters — **after
  one cache refresh**, so a function redefined at runtime resolves instead of failing.
- A function the server does not know raises `SurrealDbNotFoundError`.

**`return_type`** — any type annotation Pydantic can adapt (`BaseModel` subclass, dataclass,
`list[LockResult]`, `int`, `datetime`, …), applied with `pydantic.TypeAdapter(...)
.validate_python(value)`. One code path covers every shape. A coercion failure raises
`SurrealDbValidationError`.

**Errors** — every SDK exception is wrapped: a nonexistent function becomes
`SurrealDbNotFoundError` (matched on `does not exist`, present in both lines' wording),
everything else becomes `SurrealDbError`, with the original attached via `raise … from exc`.

## Files

- `src/surreal_orm_lite/functions.py` — pure helpers, no I/O: `normalize_function_name()`,
  `parse_function_parameters()` (DEFINE text → ordered names), `build_call_statement()`
  (name + values → `("fn::x($_fnarg0);", {"_fnarg0": …})`). This module already holds the
  server-side-computation helpers and imports nothing from the package, so it stays cycle-free.
- `src/surreal_orm_lite/connection_manager.py` — `call_function()`, the signature cache, and
  cache reset from `unset_connection()`.
- `src/surreal_orm_lite/model_base.py` — the delegating classmethod.
- `src/surreal_orm_lite/__init__.py` — version bump (no new exported symbol: the feature is
  reached through the manager and the model base, both already exported).
- `tests/test_call_function.py` — **new**: unit (name validation, signature parsing, statement
  building, arg/param exclusivity, coercion) + E2E (call, nested namespace, zero args, NONE,
  named params, typed return, missing function, wrong arity, both transaction strategies) on
  both ports.

## Acceptance criteria

1. `call_function("fn::greet", ["ada"])` returns the server's value on 8001 **and** 8002.
2. `call_function("greet", ["ada"])` — the `fn::` prefix is added — behaves identically.
3. Arguments are **bound**, never formatted: a value containing `);DELETE user;--` is passed
   through as data and the generated statement is asserted to contain only `$_fnarg…`.
4. An invalid function name (`"fn::x; DROP"`, `"fn::"`, `""`) raises `ValueError` and issues
   **no query**.
5. `params={...}` resolves declaration order from `INFO FOR DB` and returns the same value as
   the equivalent `args`; an unknown/missing key raises `ValueError` naming the parameters.
6. Passing both `args` and `params` raises `ValueError`.
7. `return_type=` coerces to a Pydantic model, a scalar, and a `list[...]`; a bad shape raises
   `SurrealDbValidationError`.
8. A nonexistent function raises `SurrealDbNotFoundError` on **both** lines (asserted on type,
   not message).
9. `tx=` inside an interactive transaction (3.x/WS) returns the value and the function's writes
   roll back when the transaction is cancelled — `pytest.skip()` on 2.6.x.
10. `tx=` inside a buffered transaction (2.6.x/HTTP) returns `None`, the function's writes land
    at commit, **and a statement queued after the call still executes** (the `RETURN` regression
    guard from the finding above).
11. `return_type=` together with a buffered `tx=` raises `ValueError`.
12. Zero-argument functions and functions returning `NONE` work.
13. Gates: `ruff format --check`, `ruff check`, `mypy src/`, coverage ≥ 70 %.
