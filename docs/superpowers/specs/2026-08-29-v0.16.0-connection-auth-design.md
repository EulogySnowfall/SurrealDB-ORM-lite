# v0.16.0 — Connection-level authentication (`signin` / `signup` / `authenticate` / `invalidate` / `info`) — Design

- **Date**: 2026-08-29
- **Status**: Approved (design)
- **Target version**: 0.16.0
- **Roadmap**: Tier 1, Phase C — Auth & DX
- **SDK primitives**: native — `client.signin()`, `client.signup()`, `client.authenticate()`,
  `client.invalidate()`, `client.info()`. All five exist on both the WebSocket and the HTTP
  connection classes of the installed SDK 2.0.0 (verified by `inspect.signature`); no
  `query()` fallback is needed.
- **Constraint**: official SDK only (`surrealdb[pydantic]>=2.0.0,<3.0.0`); all SDK imports via
  `_sdk.py`.

## Goal

Authenticate the ORM's connection as a **record user** (SurrealDB's `DEFINE ACCESS … TYPE
RECORD`) or as a different **system user**, keep that identity across reconnects, and read
back who is currently authenticated — with the SDK's inconsistent, per-DB-line errors
normalized into one ORM exception.

```python
from surreal_orm_lite import SurrealDBConnectionManager

# Register a new record user against a DEFINE ACCESS method
tokens = await SurrealDBConnectionManager.signup(
    access="account", variables={"email": "ada@example.com", "pass": "s3cret"},
)

# Authenticate an existing one
tokens = await SurrealDBConnectionManager.signin(
    access="account", variables={"email": "ada@example.com", "pass": "s3cret"},
)
tokens.access    # the JWT, to hand to a web session
tokens.refresh   # SurrealDB 3.x only (WITH REFRESH); always None on 2.6.x

# Re-attach a stored JWT on a later request
await SurrealDBConnectionManager.authenticate(stored_jwt)

# Who am I?
me = await SurrealDBConnectionManager.info(return_type=User)   # User | None

# Log out — back to the credentials given to set_connection()
await SurrealDBConnectionManager.invalidate()
```

v0.16.0 ships four things:

1. **The five auth classmethods** on `SurrealDBConnectionManager`, named by the roadmap.
2. **Session-token persistence** — the authenticated identity survives `reconnect()`, a
   dropped client and a second event loop, because `get_client()` replays it.
3. **`AuthTokens`** — an ORM-owned frozen dataclass with a redacting `__repr__`, replacing the
   SDK's `Tokens` in the public API.
4. **`SurrealDbAuthenticationError`** — one exception for every authentication failure, on
   both DB lines.

This is the connection half of the full ORM's auth support
(`surreal_orm/auth/`). The **model half** — `AuthenticatedUserMixin`, `User.signup()` /
`User.signin()` returning a hydrated model instance, and the `DEFINE ACCESS` generator — is
explicitly **v0.17.0** and out of scope here. `auth.py` is created now so v0.17.0 extends it
rather than inventing a module.

**Also out of scope, deliberately**: a `define_access()` DDL helper. Declaring an access
method is DDL and belongs with the `schema.py` module the roadmap opens at v0.31.0. Until
then an access method is declared the way the tests and the example notebook declare one:
`await client.query("DEFINE ACCESS … TYPE RECORD …;")`.

## SDK primitives used

| ORM method       | SDK call                     | Returns                       |
| ---------------- | ---------------------------- | ----------------------------- |
| `signin()`       | `client.signin(vars)`        | `surrealdb.types.Tokens`      |
| `signup()`       | `client.signup(vars)`        | `surrealdb.types.Tokens`      |
| `authenticate()` | `client.authenticate(token)` | `None`                        |
| `invalidate()`   | `client.invalidate()`        | `None`                        |
| `info()`         | `client.info()`              | the `$auth` record, or `None` |

`Tokens` is a frozen dataclass with `access: str | None` and `refresh: str | None`. The SDK
normalizes both the plain-JWT and the object response shapes into it, and stores `access` on
the connection as `self.token`.

### Empirical facts, probed on :8001 (3.2.4) and :8002 (2.6.5), over both `ws://` and `http://`

Every result below was **identical on both servers and both protocols** unless the row says
otherwise. The probes ran against a `DEFINE ACCESS … TYPE RECORD` method with an
argon2-hashed password field.

- The record signin payload the SDK expects is
  `{"namespace": …, "database": …, "access": …, "variables": {…}}`; the system-user payload is
  `{"username": …, "password": …}` (plus `namespace`/`database` for a NS- or DB-level user).
- `signin`/`signup` both return `Tokens` with a non-empty `access`, and both mutate the
  connection's session — every subsequent statement runs as that identity.
- After a record signin, `RETURN $auth` yields the record's `RecordID` and `RETURN $access`
  yields the access-method name.
- **`info()` returns `None` unless the record's table grants that record user `select` on
  itself.** With `PERMISSIONS FULL` or `PERMISSIONS FOR select WHERE id = $auth.id` it returns
  the full record dict (id, and every stored field including the password hash); with the
  default table permissions it returns `None` and raises nothing. Same on both lines.
- After `invalidate()` the session is **anonymous**: `info()` and every query fail. 3.x reports
  `Anonymous access not allowed`, 2.6.x reports `IAM error: Not enough permissions`.
- `authenticate()` re-attaches a token and restores the record identity; a system-user signin
  afterwards keeps the previously selected namespace/database.
- **`DEFINE ACCESS … WITH REFRESH` is 3.x only.** On 3.2.4 it is accepted and `signup`/`signin`
  return a populated `tokens.refresh`. On 2.6.5 the statement fails to parse —
  `Unexpected token 'RECORD', expected the experimental bearer access feature to be enabled` —
  so `tokens.refresh` is **always `None`** on 2.6.x.
- The SDK's raw errors are **not consistent across lines** — this is what makes normalization
  the feature's main job:

  | Failure                  | SurrealDB 3.2.4                                                                         | SurrealDB 2.6.5                           |
  | ------------------------ | --------------------------------------------------------------------------------------- | ----------------------------------------- |
  | wrong password           | `NotFoundError: No record was returned`                                                 | `InternalError: … No record was returned` |
  | unknown access method    | `InternalError: The access method does not exist`                                       | same wording                              |
  | malformed token          | `ValueError` raised **client-side** by the CBOR schema check — never reaches the server | same                                      |
  | `info()` while anonymous | `SurrealError: no result getting auth information`                                      | same                                      |

- **Duplicate identifier**: with two records sharing the signin identifier, 3.x signs in
  (picking one) while **2.6.x fails** with `No record was returned`. Not ORM-caused, but it
  makes E2E fixtures order-dependent, so every test row uses a unique identifier.

## Capability dispatch (3.x vs 2.6.x)

The five methods are **identical on both lines** — no probe, no degradation, no fallback path.
The single divergence is a server feature the ORM merely surfaces:

| Behaviour                                                    | SurrealDB 2.6.x                               | SurrealDB 3.x (3.2.x)                                    |
| ------------------------------------------------------------ | --------------------------------------------- | -------------------------------------------------------- |
| `signin` / `signup` / `authenticate` / `invalidate` / `info` | work identically                              | work identically                                         |
| `AuthTokens.refresh`                                         | always `None` (`WITH REFRESH` does not parse) | populated when the access method declares `WITH REFRESH` |
| Session restored across `reconnect()`                        | yes                                           | yes                                                      |
| Failure exception type                                       | `SurrealDbAuthenticationError`                | `SurrealDbAuthenticationError`                           |

The refresh-token E2E test probes the server by attempting the `WITH REFRESH` `DEFINE ACCESS`
and calls `pytest.skip()` when it does not parse — the same adaptive-skip contract v0.9.0 uses
for interactive transactions. **The ORM does not consume refresh tokens in v0.16.0**; it
carries the value through so a 3.x application can store it. Exchanging one for a new access
token is a server round trip with no SDK primitive, and is deferred.

## Public API

```python
# auth.py — pure, no I/O
@dataclass(frozen=True, slots=True)
class AuthTokens:
    access: str
    refresh: str | None = None
    def __repr__(self) -> str: ...        # both tokens redacted

def build_auth_payload(
    *,
    username: str | None,
    password: str | None,
    access: str | None,
    variables: Mapping[str, Any] | None,
    namespace: str | None,
    database: str | None,
    default_namespace: str | None,
    default_database: str | None,
) -> dict[str, Any]: ...

def wrap_auth_error(exc: Exception, operation: str) -> SurrealDbAuthenticationError: ...

# connection_manager.py
@classmethod
async def signin(cls, *, username=None, password=None, access=None, variables=None,
                 namespace=None, database=None, store=True) -> AuthTokens: ...
@classmethod
async def signup(cls, *, access, variables, namespace=None, database=None,
                 store=True) -> AuthTokens: ...
@classmethod
async def authenticate(cls, token: str, *, store: bool = True) -> None: ...
@classmethod
async def invalidate(cls) -> None: ...
@classmethod
async def info(cls, *, return_type: Any = None) -> Any: ...
@classmethod
def is_authenticated(cls) -> bool: ...
@classmethod
def get_session_token(cls) -> str | None: ...
```

**`signin()` takes one of two credential shapes**, keyword-only:

- **Record access** — `access=` plus `variables=`. `namespace`/`database` default to the
  configured ones, because the server requires them; pass them explicitly to authenticate
  against another database.
- **System user** — `username=` plus `password=`. Namespace and database are **not** injected
  by default. A root user is defined at neither level, and sending `namespace`/`database`
  would turn a root signin into a namespace- or database-user signin, which fails. Pass
  `namespace=` (and `database=`) explicitly for a NS- or DB-level user.

Argument validation happens in `build_auth_payload()` before any I/O, and raises `ValueError`:
neither shape given, both given, `access=` without `variables=`, `username=` without
`password=`, or `database=` without `namespace=`.

**`signup()`** accepts the record shape only — SurrealDB has no signup for system users.

**`AuthTokens`** guarantees a non-`None` `access` (the SDK's `Tokens` types it as optional; a
successful signin that somehow returned no token raises `SurrealDbAuthenticationError` rather
than handing back `None`). It deliberately has **no `__str__` returning the JWT** and a
`__repr__` that prints `AuthTokens(access=<redacted>, refresh=<redacted>)`, so a token cannot
leak into a log line, a pytest assertion diff or a traceback by accident. Callers read
`tokens.access` explicitly.

**`store=`** — whether the resulting token becomes the manager's remembered session. Default
`True`. Pass `store=False` to mint a token for someone else (issuing a JWT for a web client)
without changing what this process re-authenticates as on reconnect. The connection's _current_
session is mutated either way; that is the SDK's behaviour and the ORM does not hide it.

**`info(return_type=)`** coerces the `$auth` record with the same `TypeAdapter` path
`call_function(return_type=)` uses. A `None` result is returned as `None` **without**
coercion — the common cause is a table that does not grant the record user `select` on itself,
and raising a validation error there would obscure a permissions problem. A non-`None` payload
that does not fit raises `SurrealDbValidationError`.

**`invalidate()`** calls the SDK's `invalidate()`, forgets the stored token, then re-signs in
with the credentials from `set_connection()` and re-issues `use()`. Without that last step the
shared client would be left anonymous and every subsequent ORM call — on a connection the
caller never explicitly closed — would fail. The semantic is "log the record user out, back to
the application's own identity".

**Session persistence** — `get_client()` keeps its existing root signin + `use()`, then
replays `authenticate(stored_token)`. The replay runs **after** the client is cached and
**outside** the existing broad `except`, so an expired or revoked token surfaces as
`SurrealDbAuthenticationError` (with the stored token dropped) instead of being flattened into
`SurrealDbConnectionError`: the connection is fine, only the identity is gone. The client stays
cached and usable at the configured identity, so the caller can simply sign in again.

**Errors** — every SDK exception raised by these five methods becomes
`SurrealDbAuthenticationError`, which subclasses `SurrealDbError` so existing
`except SurrealDbError` handlers keep working. Matching on message substrings was rejected: the
measured wordings and types differ per line and per protocol, and these methods do nothing but
authenticate, so any failure is an authentication failure. The original is always attached via
`raise … from exc`.

**Scope warning, documented on every method**: the manager caches one client per event loop and
every model shares it. An auth call changes the identity of _all_ subsequent ORM operations on
that connection, not just the caller's. Concurrent requests in a web application must not share
one connection manager identity — that is an application-architecture concern the ORM cannot
solve, and the docstrings say so.

## Files

- `src/surreal_orm_lite/auth.py` — **new**: `AuthTokens`, `build_auth_payload()`,
  `wrap_auth_error()`. Pure and I/O-free, mirroring how `functions.py` holds the helpers for
  `call_function()`. Imports only `exceptions.py`, so it stays cycle-free — and it is the
  module v0.17.0's `AuthenticatedUserMixin` will extend.
- `src/surreal_orm_lite/exceptions.py` — `SurrealDbAuthenticationError(SurrealDbError)`.
- `src/surreal_orm_lite/connection_manager.py` — the five classmethods, the
  `__session_token` slot, the replay in `get_client()`, the reset in `unset_connection()`, and
  the generalization of `_coerce_call_result` (`function` → `subject`) so `info()` reuses it.
- `src/surreal_orm_lite/__init__.py` — export `AuthTokens` and
  `SurrealDbAuthenticationError`; version bump to 0.16.0.
- `tests/test_auth.py` — **new**: unit (payload building, argument validation, repr redaction,
  error wrapping, the `is_authenticated` state machine) + E2E on both ports.
- `examples/v0.16.0_connection_auth.ipynb` — **new**, executed with real outputs.

## Acceptance criteria

1. `signup(access=…, variables=…)` creates the record and returns an `AuthTokens` with a
   non-empty `.access`, on 8001 **and** 8002.
2. `signin(access=…, variables=…)` authenticates an existing record user on both lines, and
   `RETURN $auth` afterwards is that record.
3. `signin(username=…, password=…)` authenticates a system user and sends **no**
   namespace/database unless they are passed explicitly.
4. `info()` returns the authenticated record's fields when the table grants it `select`, and
   `None` when it does not — on both lines, raising nothing in either case.
5. `info(return_type=Model)` returns a hydrated model instance; a `None` payload returns `None`
   without a coercion error; a mismatched payload raises `SurrealDbValidationError`.
6. `authenticate(tokens.access)` restores a record identity after `invalidate()`.
7. **Token persistence**: after a record signin, `reconnect()` (or a client dropped from the
   cache) leaves `info()` reporting the _same_ record — the ORM did not silently fall back to
   the configured root identity.
8. `authenticate()` with an expired or malformed token raises `SurrealDbAuthenticationError`
   and leaves the previously stored token **untouched** — the call failed, so it changed
   nothing. Only the `get_client()` replay drops a token, and only once the server has
   rejected the one it was holding.
9. `invalidate()` returns the connection to the configured credentials: an ordinary ORM query
   succeeds immediately afterwards, with no explicit `reconnect()`.
10. Wrong password, unknown access method and malformed token all raise
    `SurrealDbAuthenticationError` on **both** lines (asserted on type, never on wording), and
    `SurrealDbAuthenticationError` is caught by `except SurrealDbError`.
11. `build_auth_payload()` raises `ValueError` — issuing **no** request — for: neither
    credential shape, both shapes, `access=` without `variables=`, `username=` without
    `password=`, `database=` without `namespace=`.
12. `repr(tokens)` contains neither token; `AuthTokens` has no `__str__` yielding the JWT.
13. `store=False` mints a token without changing `get_session_token()`.
14. `is_authenticated()` / `get_session_token()` track signin → authenticate → invalidate, and
    `unset_connection()` clears them.
15. 3.x-only: with `DEFINE ACCESS … WITH REFRESH`, `tokens.refresh` is non-`None`;
    `pytest.skip()` on 2.6.x, where the statement does not parse.
16. Gates: `ruff format --check`, `ruff check`, `mypy src/`, coverage ≥ 70 %, and the example
    notebook re-executes cleanly.

## Open questions

None. The five design risks — the payload shape per credential kind, `info()` returning `None`
under default table permissions, the per-line error types, whether `WITH REFRESH` exists on
2.6.x, and whether an anonymous session after `invalidate()` breaks the shared client — were
each settled by probing both servers over both protocols before this spec was written.
