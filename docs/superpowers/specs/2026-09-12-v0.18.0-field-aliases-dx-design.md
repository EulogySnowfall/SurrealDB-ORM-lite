# v0.18.0 — Field aliases, `server_fields` & `merge(refresh=False)` — Design

> Status: design · Target version: **v0.18.0** · Roadmap: Tier 1, Phase C — Auth & DX
> Roadmap row: _Field aliases (`Field(alias=)`) + `server_fields` + `merge(refresh=False)`_

## 1. Goals

Three developer-experience features that together let a model's **Python surface** differ from
its **SurrealDB column surface**, and let a caller skip work they do not need.

1. **Field aliases** — `password: str = Field(alias="password_hash")` maps a Python attribute to
   a differently-named SurrealDB column. The alias is honoured on **every** boundary: writes,
   reads/hydration, and — the part the full ORM still lists as an open gap — **query filters**,
   `order_by`, `values()`, `fetch()`, the aggregation helpers and `bulk_update()`.
2. **`server_fields`** — `model_config = SurrealConfigDict(server_fields=["created_at"])` marks
   columns the **server** owns. They are dropped from implicit write payloads (so the client
   never clobbers a server default), hydrated back after a write, and remain explicitly
   writable when the caller names one.
3. **`merge(refresh=False)`** — skip the post-merge resync round-trip for fire-and-forget
   updates (presence pings, counters, `last_seen`).

### Non-goals

- Pydantic's `AliasPath` / `AliasChoices` / separate `validation_alias` + `serialization_alias`.
  Only a plain, symmetric `Field(alias=…)` describes a *column rename*, which is the feature
  here. Anything else is left to Pydantic and is explicitly unsupported by the ORM's mapping.
- DDL generation from aliases (`DEFINE FIELD`); computed-field DDL keeps using the names it
  already uses. Schema introspection is v0.30.0.
- Aliasing the `id` / primary-key column.

## 2. SDK primitives used

**None that are new.** All three features are client-side: Pydantic's own alias machinery plus
the SurrealQL the ORM already emits. No new SDK method, so nothing is added to `_sdk.py`.

- Aliases: `pydantic.fields.FieldInfo.alias`, `model_dump(by_alias=True)`,
  `ConfigDict(populate_by_name=True)`.
- `server_fields`: `model_dump(exclude=…)`.
- `refresh=False`: skipping the existing `refresh()` call; on the `server_values` path, the
  standard SurrealQL `RETURN NONE` suffix.

## 3. Capability dispatch (3.x vs 2.6.x)

**There is none — and that is the point.** Every one of the three features is either pure
Python (alias mapping, payload exclusion) or plain SurrealQL valid on both server lines
(`UPDATE … MERGE`, `UPDATE … SET … RETURN NONE`). The behaviour is **identical on SurrealDB
2.6.x and 3.x**, in and out of a transaction, so:

- no capability probe is added;
- no test needs `pytest.skip()` for this version;
- the README behaviour table gets an explicit _"same on both lines"_ row, so a reader is not
  left guessing whether silence means untested.

The only line-dependent behaviour the features **inherit** is the pre-existing transaction
split: inside a *buffered* transaction (HTTP or 2.6.x) nothing runs before commit, so
`merge(tx=…)` already applies data locally instead of resyncing — which is exactly what
`refresh=False` does everywhere else. `refresh=False` therefore makes the non-tx path behave
like the buffered-tx path already does, narrowing a difference rather than adding one.

## 4. Public API

### 4.1 Aliases

Declaration is plain Pydantic — the ORM adds no new declaration syntax:

```python
class User(BaseSurrealModel):
    id: str
    password: str = Field(alias="password_hash")
    display: str = Field(alias="display_name")
```

`BaseSurrealModel` gains `model_config = ConfigDict(populate_by_name=True)` so an instance can
be built by **either** name — `User(password="x")` in application code, `User(password_hash="x")`
when hydrating a DB row. This is strictly widening: before v0.18.0 an aliased field could only
be populated by its alias.

Three classmethods expose the mapping (all cached per class):

| Method | Returns |
| --- | --- |
| `get_field_aliases()` | `{python_name: column}` for fields that declare an alias (`{}` otherwise) |
| `to_db_field(name)` | the column for `name`; `name` unchanged when unaliased |
| `to_py_field(column)` | the Python attribute for `column`; `column` unchanged when unmapped |

`to_db_field` / `to_py_field` translate only the **first segment** of a dotted path, so
`address.city` maps through `address` — the same rule the computed-field and atomic-op guards
already apply to nested paths.

### 4.2 `server_fields`

```python
class Post(BaseSurrealModel):
    model_config = SurrealConfigDict(server_fields=["created_at", "updated_at"])
    id: str
    title: str
    created_at: datetime | None = None
```

`get_server_fields() -> frozenset[str]` returns the configured names **merged with the model's
computed fields** — a computed field is server-owned by construction, so the two collapse into
one "the server owns this column" set that every write path consults. Names must be declared
fields; an unknown name raises `ValueError` naming the offender (a typo'd `server_fields` entry
would otherwise silently protect nothing).

Semantics, and how they differ from a computed field:

| | computed field (`Computed[...]`) | `server_fields` entry |
| --- | --- | --- |
| Dropped from implicit writes (`save`/`update`/`upsert`) | yes | yes |
| Hydrated back from the returned row | yes | yes |
| Explicit write (`merge(x=…)`, `bulk_update(x=…)`, `server_values`) | **raises** | **allowed** |

The split is deliberate. A computed field is defined by `DEFINE FIELD … VALUE`, so the server
*discards* a client write — raising turns an invisible no-op into an error. A `server_fields`
entry is merely a column the ORM is told not to volunteer; writing it is a legitimate,
deliberate act (a backfill, an admin correction), so naming it is taken as consent.

### 4.3 `merge(refresh=…)`

```python
async def merge(
    self,
    tx: Transaction | None = None,
    server_values: Mapping[str, SurrealFunc] | None = None,
    extra_vars: Mapping[str, Any] | None = None,
    refresh: bool = True,
    **data: Any,
) -> Any: ...
```

`refresh` is appended **after** the existing parameters so no positional call changes meaning.
It joins `tx` / `server_values` / `extra_vars` in the method's documented reserved-keyword list.

`refresh=False` means *do not sync this instance from the server*:

| path | `refresh=True` (default) | `refresh=False` |
| --- | --- | --- |
| native, no tx | `client.merge()` then `refresh()` (extra SELECT) | `client.merge()` only; `data` applied locally |
| `server_values`, no tx | `UPDATE … SET` returns the row, applied | `UPDATE … SET … RETURN NONE`; literal `data` applied locally |
| interactive tx (3.x) | `refresh(tx=)` / returned row applied | returned row not requested; `data` applied locally |
| buffered tx (HTTP/2.6.x) | already local-only | unchanged |

**Documented cost:** the "no rows came back ⇒ record not found" check disappears under
`refresh=False`, on every path. That check is the returned row, and `refresh=False` is a request
not to pay for it. A caller who needs to know the record exists must keep the default.

## 5. Where the alias translation happens

One rule: **Python names in, column names on the wire.** The translation sits at each boundary,
never in between, so no intermediate layer has to know which convention it is holding.

| Boundary | Change |
| --- | --- |
| `_write_payload()` | `model_dump(by_alias=True, exclude={"id", *get_server_fields()})` |
| `_do_save` / `_do_upsert` / `update` | unchanged — they consume `_write_payload()` |
| `_do_save_server`, `_merge_server` | `server_values` keys translated before `build_set_clause` |
| `merge(**data)` | keys translated for the wire payload; the local apply keeps Python names |
| `_apply_record`, `refresh`, the inline hydration loops | column → Python before `setattr` |
| `QuerySet.filter`, `order_by`, `values`, `fetch`, `sum/avg/min/max`, `bulk_update` | field → column |
| `Q.to_sql` | new optional `field_map` argument, passed down recursively by the QuerySet |

Hydration is consolidated: `_do_save` and `refresh()` currently carry their own
`for key, value in record.items(): if hasattr(self, key)` loops. Those become `_apply_record`
calls, so alias translation is written once and cannot drift between write paths.

## 6. Acceptance criteria

1. A model with `Field(alias=…)` round-trips: `save()` stores under the **column**, a fresh
   `objects().filter(python_name=…)` finds it, and the hydrated instance exposes the **Python**
   attribute. Verified E2E on 8001 and 8002.
2. `merge()`, `upsert()`, `update()`, `patch()`, `bulk_update()`, `order_by()`, `values()` and
   the aggregation helpers all address the aliased column, not the Python name.
3. `User(password="x")` and `User(password_hash="x")` both validate (`populate_by_name`).
4. `server_fields` entries never appear in a `save()`/`update()`/`upsert()` payload, are
   hydrated back after the write, and remain writable when named explicitly.
5. An unknown name in `server_fields` raises `ValueError` naming it.
6. A computed field still raises on an explicit write; a `server_fields` entry does not.
7. `merge(refresh=False)` performs no second round-trip, leaves the instance holding the merged
   `data`, and works identically on both DB lines; the default stays `True` and unchanged.
8. Coverage ≥ 70 %, `ruff format --check`, `ruff check`, `mypy src/` all green; full suite green
   on 8001 **and** 8002; no test is skipped for this feature on either line.
